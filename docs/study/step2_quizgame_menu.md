## 3-1. QuizGame의 책임과 초기 상태

### 시작하기 전에: Step 1의 문제가 실제로 해결됐습니다

Step 2 코드를 보기 전에 먼저 확인할 것이 있습니다. Step 1 학습 노트(`docs/study/step1_quiz_model.md`)에서는 `Quiz` 클래스가 `main.py` 안에 들어 있는데 `storage.py`는 `from quiz import Quiz, get_default_quizzes`로 존재하지 않는 `quiz.py`를 가져오려 해서 임포트가 깨진다는 문제를 지적했었습니다. 지금 저장소를 확인해 보면 이 문제는 실제로 고쳐져 있습니다. `Quiz` 클래스와 `get_default_quizzes()`가 새로 만들어진 `quiz.py`(166줄)로 옮겨졌고, `main.py`도 `from quiz import Quiz, get_default_quizzes`로 정상적으로 가져다 씁니다. 직접 확인해 보면:

```bash
$ python3 -c "import storage"
storage import OK
```

지적받은 구조적 문제를 다음 단계에서 실제로 바로잡았다는 것은, "일단 돌아가게만 만들기"가 아니라 책임에 맞는 위치로 코드를 옮기는 리팩터링을 스스로 실천했다는 뜻이라 눈여겨볼 만합니다.

### QuizGame이 지는 책임

`QuizGame`은 메뉴 출력부터 종료까지, 이 프로그램의 전체 흐름을 담당하는 하나의 클래스입니다. "전체 흐름을 관리한다"는 말은 구체적으로 무엇을 뜻할까요? QuizGame은 (1) 어떤 데이터를 들고 있을지(퀴즈 목록, 최고 점수)와 (2) 사용자가 메뉴에서 무엇을 고르면 어떤 메서드로 넘길지를 결정하는 역할을 합니다. 실제 데이터를 어떻게 저장·출력할지는 `Quiz`나 `storage.py`에 위임하고, QuizGame 자신은 "무엇을 언제 부를지"만 조율합니다.

### `__init__`의 초기화 순서

```python
def __init__(self) -> None:
    self.quizzes: list[Quiz] = []
    self.best_score: int = 0
    self.best_correct: int = 0
    self.best_total: int = 0

    self.load_state()
```

여기서 순서가 중요합니다. 네 개의 속성을 먼저 빈 값/기본값으로 초기화한 다음, 마지막 줄에서 `self.load_state()`를 호출합니다. 이렇게 하면 인스턴스가 항상 완전한 상태로 시작한다는 것을 보장할 수 있습니다 — `load_state()`가 어떤 이유로든 값을 채우지 못하더라도(예: 저장 파일이 아직 없는 최초 실행) `self.quizzes`나 `self.best_score` 같은 속성이 아예 존재하지 않는 상황은 생기지 않습니다. 먼저 안전한 기본값을 만들어 두고, 그 위에 저장된 값을 덮어쓰는 순서입니다.

다만 한 가지는 정직하게 짚어야 합니다. `self.best_correct`와 `self.best_total`은 변수로는 분명히 초기화되지만, 실제로 `storage.py`의 `load_state()`/`save_state()`를 열어보면 이 두 값을 전혀 다루지 않습니다.

```python
def load_state(state_file: Path | str = STATE_FILE) -> tuple[list[Quiz], int]:
    ...  # quizzes와 best_score 두 개만 반환한다

def save_state(quizzes: list[Quiz], best_score: int, state_file: Path | str = STATE_FILE) -> bool:
    ...  # quizzes와 best_score만 저장한다
```

즉 `QuizGame.load_state()`가 실행되면 `self.quizzes`와 `self.best_score`만 저장된 값으로 바뀌고, `self.best_correct`와 `self.best_total`은 `__init__`에서 넣은 `0`이 그대로 유지됩니다. 프로그램을 껐다 켜도 이 두 값은 항상 0으로 리셋됩니다. 이것은 버그가 아니라 아직 배선이 끝나지 않은 부분이라고 이해하는 게 정확합니다. 체크리스트 3-1은 "최고 기록의 정답 수·전체 문제 수도 보여 줄 계획이면 초기화"까지만 요구하고 있고, 이 값을 실제로 파일에 저장하고 불러오는 것은 점수 계산 로직이 들어가는 이후 단계의 몫이기 때문입니다. Step 2는 메뉴 골격과 입력 처리까지만 다루기로 되어 있으므로, 지금 시점에서 `best_correct`/`best_total`이 "그릇만 준비되고 아직 채워지지 않은" 상태인 것은 자연스러운 일입니다.

### 메서드를 왜 이렇게 쪼갰는가

체크리스트는 "모든 코드를 하나의 함수에 몰아넣지 않는다"고 요구합니다. `main.py`를 열어 보면 이 요구가 실제로 메서드 단위 분리로 지켜지고 있다는 것을 확인할 수 있습니다.

| 메서드 | 책임 |
|---|---|
| `show_menu` | 1~5번 메뉴 문구를 화면에 출력 |
| `run` | 메뉴를 반복 표시하고 선택값에 따라 다른 메서드로 분기 |
| `ask_int` | 지정한 범위의 정수를 받을 때까지 재시도하는 공통 입력 헬퍼 |
| `ask_text` | 빈 문자열이 아닌 텍스트를 받을 때까지 재시도하는 공통 입력 헬퍼 |
| `play_quiz` | 1번 메뉴 — 퀴즈 풀기(현재는 준비 중 안내만) |
| `add_quiz` | 2번 메뉴 — 퀴즈 추가(현재는 준비 중 안내만) |
| `show_quiz_list` | 3번 메뉴 — 퀴즈 목록(현재는 준비 중 안내만) |
| `show_score` | 4번 메뉴 — 점수 확인(현재는 준비 중 안내만) |
| `save_state` | 현재 `self.quizzes`, `self.best_score`를 파일에 저장 |
| `load_state` | 파일에서 값을 불러와 `self.quizzes`, `self.best_score`를 채움 |

이렇게 나누면 각 메서드는 딱 하나의 질문에만 답합니다. "화면에 뭘 보여줄까"(`show_menu`), "다음에 뭘 실행할까"(`run`), "입력이 유효한가"(`ask_int`/`ask_text`), "이 메뉴 항목이 실제로 하는 일은 무엇인가"(`play_quiz` 등), "데이터를 어떻게 디스크와 주고받을까"(`save_state`/`load_state`) 로 관심사가 분리되어 있습니다. 만약 이 모든 것이 `main()` 함수 하나에 뒤섞여 있었다면, 예를 들어 입력 검증 로직을 고치려다가 메뉴 출력 순서까지 실수로 건드릴 위험이 커집니다. 메서드로 나눠 두면 어떤 기능을 고치거나 테스트할 때 그 메서드 하나만 들여다보면 되고, 나중에 `play_quiz`에 실제 퀴즈 로직을 채워 넣을 때도 다른 메서드를 건드릴 필요가 없습니다.

### `as` 별칭을 쓴 이유

`main.py` 맨 위를 보면 다음과 같이 임포트합니다.

```python
from storage import load_state as load_quiz_state
from storage import save_state as save_quiz_state
```

그런데 `QuizGame` 클래스에는 똑같은 이름의 메서드 `load_state`, `save_state`가 있습니다.

```python
def save_state(self) -> bool:
    return save_quiz_state(self.quizzes, self.best_score)

def load_state(self) -> None:
    self.quizzes, self.best_score = load_quiz_state()
```

만약 별칭 없이 `from storage import load_state`로 그냥 가져왔다면, 모듈 최상위 이름공간에 있는 함수 `load_state`와 `QuizGame` 클래스 안의 메서드 `load_state`가 이름은 같지만 서로 다른 대상이라, 클래스 본문 안에서 `load_state()`라고만 쓰면 파이썬이 어느 쪽을 가리키는지 헷갈릴 여지가 생깁니다(실제로는 메서드 안에서 `self.load_state()`처럼 `self.`를 붙이므로 완전히 깨지지는 않지만, 같은 이름이 두 군데 존재한다는 사실 자체가 코드를 읽는 사람을 헷갈리게 합니다). `load_quiz_state`, `save_quiz_state`처럼 "이건 storage 모듈에서 온 순수 함수"라고 이름으로 표시해 두면, `self.load_state()`(QuizGame의 메서드, 흐름을 관장)와 `load_quiz_state()`(storage의 함수, 실제로 파일을 읽고 씀)를 코드만 보고도 혼동 없이 구분할 수 있습니다. 이름이 겹치는 상황을 `as` 별칭으로 미리 피해 둔 것입니다.

## 3-2. ask_int: 숫자 입력 재시도 규칙

### 왜 `ask_int`가 필요한가

터미널 프로그램에서 사용자 입력은 절대로 믿을 수 없습니다. 숫자를 물어봤는데 문자를 입력하거나, 빈 줄만 누르거나, 범위를 벗어난 숫자를 넣는 일은 흔히 일어납니다. 이런 모든 경우에 프로그램이 그대로 죽어버리면(예: `ValueError`가 처리되지 않아 프로그램이 종료되는 것) 사용성이 매우 떨어집니다. `ask_int(self, prompt, low, high)`는 "유효한 숫자가 들어올 때까지 같은 질문을 반복한다"는 규칙을 한 곳에 모아두는 함수입니다. 실제로 `main.py`에는 이렇게 구현되어 있습니다.

```python
def ask_int(self, prompt: str, low: int, high: int) -> int:
    """low~high 범위의 정수를 입력받을 때까지 재시도한다.

    ValueError만 처리하여 KeyboardInterrupt와 EOFError는
    상위 실행 흐름에서 안전하게 처리할 수 있도록 그대로 전달한다.
    """
    while True:
        raw = input(prompt).strip()
        if not raw:
            print("⚠️ 입력이 비어 있습니다. 다시 입력하세요.")
            continue

        try:
            value = int(raw)
        except ValueError:
            print("⚠️ 숫자를 입력하세요.")
            continue

        if low <= value <= high:
            return value

        print(f"⚠️ {low}~{high} 사이의 숫자를 입력하세요.")
```

### 루프를 다섯 단계로 나눠 보기

`while True` 안에서 매번 다음 다섯 단계가 순서대로 일어납니다.

1. **공백 제거** — `input(prompt).strip()`으로 앞뒤 공백을 지웁니다. `"  2  "`를 입력해도 `strip()`이 `"2"`로 바꿔주므로, 뒤이은 `int("2")`가 정상적으로 `2`를 만듭니다. 사용자가 실수로 스페이스바를 먼저 누르거나 붙여넣기를 하면서 공백이 섞여도 문제없이 처리됩니다.
2. **빈 문자열 검사** — `if not raw:`로 공백 제거 후 아무것도 남지 않았는지 확인합니다. 그냥 Enter만 친 경우가 여기 해당하며, 안내 문구를 출력하고 `continue`로 같은 루프의 처음(`while True`)으로 돌아갑니다.
3. **`int(raw)` 변환을 `try/except ValueError`로 감싸기** — 여기가 이 함수의 핵심입니다. `int()` 변환이 실패할 수 있는 유일한 경우를 `ValueError` 하나로 좁혀서 처리합니다.
4. **범위 검사** — 변환에 성공한 값이 `low <= value <= high` 범위 안에 있는지 확인합니다.
5. **return** — 범위까지 통과하면 그제서야 `int` 값을 반환하며 루프를 빠져나갑니다. 범위를 벗어나면 안내 문구만 출력하고 `continue` 없이도 `while True`가 다시 처음부터 돌기 때문에 자동으로 재입력을 받게 됩니다.

### 실제 로그와 코드 분기 짝짓기

FACTS 5)의 실제 터미널 로그를 이 다섯 단계에 정확히 대응시켜 보면 다음과 같습니다.

| 입력 | 로그 메시지 | 대응 분기 |
|---|---|---|
| `abc` | `⚠️ 숫자를 입력하세요.` | 3단계, `int("abc")`가 `ValueError` |
| `1.5` | `⚠️ 숫자를 입력하세요.` | 3단계, `int("1.5")`가 `ValueError` |
| `9` | `⚠️ 1~5 사이의 숫자를 입력하세요.` | 4단계, `9`는 변환은 되지만 `high=5` 초과 |
| `0` | `⚠️ 1~5 사이의 숫자를 입력하세요.` | 4단계, `0`은 변환은 되지만 `low=1` 미만 |
| `-1` | `⚠️ 1~5 사이의 숫자를 입력하세요.` | 4단계, `-1`은 변환은 되지만 `low=1` 미만 |

여기서 `1.5`가 `abc`와 똑같이 "숫자를 입력하세요" 메시지로 처리된다는 점을 눈여겨봐야 합니다. 파이썬의 `int()`는 소수점이 포함된 문자열을 직접 정수로 바꿔주지 않습니다. `int("1.5")`를 실행하면 `float("1.5")`처럼 실수로 파싱해주는 게 아니라 그냥 `ValueError: invalid literal for int() with base 10: '1.5'`를 던집니다. 그래서 `1.5`도 `9`나 `0`처럼 "범위를 벗어난 숫자"가 아니라 `abc`와 같은 "애초에 숫자로 변환 자체가 안 되는 입력"으로 분류되어 3단계에서 걸러집니다. 이 프로젝트의 로그가 정확히 그렇게 찍혀 있는 것이 이 동작을 뒷받침합니다.

### 가장 중요한 포인트: `except ValueError`만 잡는다

체크리스트의 "`except:` 또는 `except Exception:`으로 KeyboardInterrupt·EOFError까지 무심코 삼키지 않음"이라는 항목은 초심자가 오해하기 쉬운 부분입니다. 이 요구사항은 코드를 더 추가해서 만족시키는 게 아니라, **정반대로 `except` 절의 범위를 `ValueError` 하나로 좁게 유지해서, 즉 아무것도 더 하지 않아서** 만족됩니다.

파이썬에서 `KeyboardInterrupt`(Ctrl+C)와 `EOFError`(입력 스트림 종료, 예: Ctrl+D)는 `Exception`과 별개의 예외 계층에 있지 않지만(`KeyboardInterrupt`는 `BaseException` 직속이라 `except Exception:`으로도 못 잡고, `EOFError`는 `Exception`의 하위라 `except Exception:`으로 잡힙니다), 어느 쪽이든 만약 `ask_int` 안에서 `except Exception:`이나 맨 `except:`를 썼다면 이 두 예외까지 조용히 삼켜버려서 프로그램이 사용자의 종료 의사를 무시하고 계속 입력을 요구하는 오작동이 생길 수 있습니다. 실제 코드는 `except ValueError:` 딱 한 줄만 쓰고 있기 때문에, `KeyboardInterrupt`나 `EOFError`가 발생하면 `ask_int`가 이를 처리하지 못하고 그대로 위로 던져 올립니다. 이렇게 올라간 예외는 `run()`을 거쳐 최종적으로 `main()`의 `try/except KeyboardInterrupt` / `except EOFError` 블록에서 붙잡혀 `_save_before_exit()`로 안전하게 저장 후 종료됩니다. FACTS 5)의 로그에서 `선택: ^C` 다음에 곧바로 `⚠️ 사용자에 의해 프로그램이 중단되었습니다. (Ctrl+C)`가 뜨고 `💾 현재 데이터를 저장하고 종료합니다.`로 이어지는 것이 바로 이 전달 경로가 실제로 동작한다는 증거입니다.

### 범용 함수로서의 `ask_int`

`ask_int`는 `low`, `high`를 인자로 받기 때문에 특정 메뉴 하나에만 묶여 있지 않습니다. 지금 코드에서 활성화된 호출 지점은 `run()`의 `self.ask_int("선택: ", 1, 5)` 하나뿐이며, 이것이 FACTS 5)의 `9`/`0`/`-1` 입력 시 "1~5 사이의 숫자를 입력하세요"가 뜨는 이유입니다. `play_quiz()`는 아직 `"🚧 [퀴즈 풀기] 기능 준비 중입니다."`만 출력하는 자리표(stub) 상태이지만, 나중에 정답 선택지가 4개인 문제(1~4번)를 처리하게 되면 같은 함수를 `self.ask_int("정답 번호: ", 1, 4)` 형태로 그대로 재사용할 수 있습니다. 공백 제거, 빈 문자열 검사, `ValueError` 처리, 범위 검사, `KeyboardInterrupt`/`EOFError` 전달이라는 다섯 가지 규칙을 매번 새로 작성할 필요 없이, 범위 숫자 두 개만 바꿔서 재사용하는 것이 이 함수를 별도로 뽑아 놓은 이유입니다.

### 흔한 실수

- `except Exception:`이나 맨 `except:`로 바꾸면 당장은 더 안전해 보이지만, `Ctrl+C`나 `Ctrl+D`가 씹히는 심각한 회귀가 생깁니다. 반드시 `ValueError`로 좁혀야 합니다.
- `int(raw)` 호출을 `try` 블록 바깥에 두면 `abc`나 `1.5` 입력에서 프로그램이 그대로 죽습니다.
- 범위를 벗어났을 때 `continue`를 빼먹어도 `while True` 구조상 다음 반복으로 자연히 넘어가지만, 안내 문구 뒤에 `return`을 실수로 넣으면 잘못된 값을 그대로 반환해버리니 주의해야 합니다.
- `"  2  ".strip()` 같은 공백 처리는 사소해 보이지만, 이 단계를 빼면 사용자가 복사·붙여넣기를 할 때 공백 하나 때문에 "숫자를 입력하세요" 오류가 반복적으로 뜨는 원인이 됩니다.

## 3-3. ask_text, 메뉴, 실행 루프

### ask_int와 닮았지만 더 단순한 ask_text

Step 2의 앞부분(3-2)에서 만든 `ask_int()`는 "빈 값 검사 → 정수 변환 시도(`try/except`) → 범위 검사"라는 세 단계를 거쳤습니다. 이번에 만드는 `ask_text()`는 그중 가운데 단계, 즉 **정수로 바꾸는 과정이 통째로 빠집니다.** 사용자가 무엇을 입력하든 문자열 그대로 받아도 되는 상황(퀴즈 문제, 보기, 정답 등을 입력받을 때)에서는 "변환에 실패할 가능성" 자체가 없기 때문입니다. `int("abc")`는 예외를 던지지만 `str("abc")`는 애초에 실패할 일이 없으므로, `ask_text()`에는 `try/except ValueError` 블록이 필요하지 않습니다.

실제 코드는 다음과 같습니다.

```python
def ask_text(self, prompt: str) -> str:
    """비어 있지 않은 문자열을 입력받을 때까지 재시도한다."""
    while True:
        text = input(prompt).strip()
        if text:
            return text
        print("⚠️ 입력이 비어 있습니다. 내용을 입력하세요.")
```

체크리스트 원문의 "raw = input(prompt).strip()"과 실제 변수명(`text`)이 다르긴 하지만, 구조는 정확히 일치합니다.

1. `input(prompt).strip()`으로 앞뒤 공백을 제거합니다. 사용자가 `"  퀴즈 제목  "`처럼 무심코 공백을 섞어 입력해도 저장되는 값은 깔끔한 `"퀴즈 제목"`이 됩니다.
2. `if text:` — 파이썬에서 빈 문자열 `""`은 `False`로 취급되므로, 공백만 입력하고 엔터를 친 경우(`strip()` 후 빈 문자열이 된 경우)에도 이 조건은 거짓이 되어 아래 `print` 문으로 안내 메시지를 띄우고 `while` 문의 다음 반복으로 넘어갑니다(체크리스트의 "continue"에 해당하는 동작이 `if`의 `else` 격인 흐름으로 자연스럽게 구현되어 있습니다).
3. 값이 있으면 그 즉시 `return text`로 함수를 끝내고 유효한 문자열을 호출한 쪽에 돌려줍니다.

즉 `ask_int`와 `ask_text`는 "공백 제거 → 빈 값이면 다시 물어보기 → 유효하면 반환"이라는 뼈대를 공유하지만, `ask_int`에는 그 사이에 "숫자로 변환되는지"와 "범위 안에 있는지"라는 두 개의 검사가 더 끼어 있는 것이라고 이해하면 됩니다. 검증해야 할 조건이 늘어날수록 함수 본문이 길어지는 것뿐, 기본 패턴은 같습니다.

### show_menu — 실제 출력과 코드를 나란히 보기

`show_menu()`는 화면에 메뉴를 그리는 역할만 담당하고, 입력을 받거나 분기하지 않습니다. 실제 코드는 다음과 같습니다.

```python
def show_menu(self) -> None:
    """자료구조 퀴즈 게임의 1~5번 메뉴를 출력한다."""
    print("\n" + "=" * 40)
    print("      🎯 자료구조 퀴즈 게임 🎯")
    print("=" * 40)
    print("1. 퀴즈 풀기")
    print("2. 퀴즈 추가")
    print("3. 퀴즈 목록")
    print("4. 점수 확인")
    print("5. 종료")
    print("=" * 40)
```

그리고 사용자가 실제로 `python3 main.py`를 실행했을 때 터미널에 찍힌 로그는 다음과 같았습니다.

```
========================================
      🎯 자료구조 퀴즈 게임 🎯
========================================
1. 퀴즈 풀기
2. 퀴즈 추가
3. 퀴즈 목록
4. 점수 확인
5. 종료
========================================
선택: 1
```

코드와 로그를 나란히 놓고 보면 한 줄씩 정확히 대응합니다. `"=" * 40`은 등호 40개짜리 구분선을 만들고, 제목은 그 사이에 들어가 메뉴 전체가 하나의 "박스"처럼 보이게 합니다. 체크리스트가 요구한 "자료구조 퀴즈 게임임을 알 수 있는 제목"은 `🎯 자료구조 퀴즈 게임 🎯`이라는 문자열로 정확히 충족되어 있으며, 1번부터 5번까지의 항목도 체크리스트가 요구한 문구(퀴즈 풀기 / 퀴즈 추가 / 퀴즈 목록 / 점수 확인 / 종료)와 한 글자도 다르지 않게 구현되어 있습니다.

### run() — while 루프와 if/elif/elif/elif/else

`run()`은 프로그램이 종료되기 전까지 메뉴를 계속 보여주는 진입점입니다.

```python
def run(self) -> None:
    """메뉴를 반복 표시하고 선택한 기능으로 분기한다."""
    while True:
        self.show_menu()
        choice = self.ask_int("선택: ", 1, 5)

        if choice == 1:
            self.play_quiz()
        elif choice == 2:
            self.add_quiz()
        elif choice == 3:
            self.show_quiz_list()
        elif choice == 4:
            self.show_score()
        else:
            self.save_state()
            print("\n👋 프로그램을 종료합니다. 이용해 주셔서 감사합니다!")
            return
```

`while True:`는 명시적으로 멈추라는 코드를 만나기 전까지 무한히 반복하는 루프입니다. 매 반복마다 `show_menu()`로 메뉴를 다시 그리고, `ask_int("선택: ", 1, 5)`로 1~5 사이의 정수를 받아옵니다. 여기서 `ask_int`는 3-2에서 이미 만든 함수를 그대로 재사용하고 있으며, 이는 "메뉴 선택에 ask_int 또는 동등한 범위 검증 사용"이라는 체크리스트 항목을 정확히 만족합니다.

주목할 부분은 마지막 `else`입니다. 코드를 보면 `choice == 5`를 직접 검사하는 조건문이 어디에도 없습니다. 그런데도 안전하게 5번(종료) 로직으로 연결되는 이유는, `ask_int("선택: ", 1, 5)`가 **1부터 5까지의 정수만 반환하도록 이미 보장**하고 있기 때문입니다. `choice`가 1, 2, 3, 4 중 어느 것도 아니라면 — `ask_int`의 약속(invariant)에 의해 — 남는 가능성은 5뿐입니다. 그래서 `elif choice == 5:`라고 다시 쓰지 않고 그냥 `else:`로 처리해도 논리적으로 틀릴 수가 없습니다.

이 부분은 "한쪽 함수가 만들어 둔 보장을 다른 쪽 코드가 신뢰하고 활용한다"는 프로그래밍의 흔한 설계 패턴을 보여주는 좋은 예입니다. `ask_int` 내부에서 범위를 벗어난 값은 절대 반환되지 않도록 이미 걸러 놓았기 때문에, `run()`은 그 뒷단에서 "혹시 6이나 0이 들어오면 어떡하지"라는 방어 코드를 다시 짤 필요가 없습니다. 검증 책임을 입력을 받는 함수(`ask_int`) 쪽에 한 번만 모아두고, 그 결과를 쓰는 함수(`run`)는 그 보장을 믿고 더 단순하게 작성하는 것입니다. 다만 이런 생략은 `ask_int`가 정말로 1~5만 반환한다는 확신이 있을 때만 안전하다는 점은 기억해 둘 필요가 있습니다. 만약 나중에 메뉴 항목이 6개로 늘어나는데 `run()`의 `ask_int` 호출 범위를 `(1, 5)`에서 `(1, 6)`으로 고치는 것을 깜빡한다면, `else` 분기는 여전히 "5번"이라고 믿고 동작하겠지만 실제로 사용자가 고를 수 있는 값은 1~6이 되어버려 두 코드 사이의 약속이 어긋나게 됩니다. `else`로 생략한 만큼, 범위를 바꿀 때는 그 값을 쓰는 쪽도 함께 점검해야 합니다.

마지막으로 5번을 선택했을 때의 흐름을 보면, `self.save_state()`를 호출해 현재까지의 퀴즈 목록과 최고 점수를 파일에 저장한 뒤, 종료 인사를 출력하고 `return`으로 `run()` 함수 자체를 끝냅니다. `return`은 `while True:` 루프를 포함해 `run()` 함수 전체를 즉시 빠져나가므로, `break`를 따로 쓸 필요 없이 한 번에 "루프 종료 + 함수 종료"가 이루어집니다. 이 흐름은 체크리스트의 "선택 5에서 현재 상태를 저장할 수 있는 범위에서 저장하고 루프를 끝내는지 확인" 항목을 정확히 만족하며, 사용자가 실제로 붙여넣은 로그에서도 `선택: 5` 다음에 곧바로 `👋 프로그램을 종료합니다. 이용해 주셔서 감사합니다!`가 출력되고 프로그램이 끝나는 것으로 확인됩니다.

## 3-4. Ctrl+C·EOF 안전 종료

### 왜 이 처리가 필요한가

터미널 프로그램은 사용자가 언제든 `Ctrl+C`(SIGINT)를 눌러 중단하거나, 입력 스트림을 닫아 `EOF`(End Of File)를 보낼 수 있습니다. 파이썬은 이 두 상황을 각각 `KeyboardInterrupt`와 `EOFError`라는 예외로 변환해서 실행 중인 코드에 던집니다. 아무 처리도 하지 않으면 파이썬은 기본 동작대로 아래처럼 긴 Traceback을 화면에 쏟아내고 죽어버립니다.

```
Traceback (most recent call last):
  File "main.py", line 123, in <module>
    main()
  ...
KeyboardInterrupt
```

일반 사용자 입장에서는 이 메시지가 "프로그램이 고장났다"는 인상을 줍니다. 사실은 정상적인 종료 요청인데 말이죠. 그래서 체크리스트는 "최상위 `main()` 또는 동등한 진입점에서" 이 두 예외를 붙잡아, Traceback 대신 사람이 읽을 수 있는 안내 메시지를 보여주고, 가능하면 `save_state()`로 데이터를 지킨 뒤 조용히 종료하라고 요구합니다.

### 이 프로젝트의 실제 구현: main() 함수

FACTS에서 확인한 `main.py`의 `main()` 함수 전체는 다음과 같습니다.

```python
def _save_before_exit(game: QuizGame) -> None:
    """예상하지 못한 종료 전에 가능한 범위에서 현재 상태를 저장한다."""
    if game.save_state():
        print("💾 현재 데이터를 저장하고 종료합니다.")
    else:
        print("⚠️ 데이터를 저장하지 못했지만 프로그램을 종료합니다.")


def main() -> None:
    """터미널 퀴즈 게임을 실행하고 종료 입력을 안전하게 처리한다."""
    game: QuizGame | None = None

    try:
        game = QuizGame()
        game.run()
    except KeyboardInterrupt:
        print("\n⚠️ 사용자에 의해 프로그램이 중단되었습니다. (Ctrl+C)")
        if game is not None:
            _save_before_exit(game)
    except EOFError:
        print("\n⚠️ 입력 스트림이 종료되었습니다. (EOF)")
        if game is not None:
            _save_before_exit(game)


if __name__ == "__main__":
    main()
```

가장 먼저 눈여겨볼 부분은 `game: QuizGame | None = None`을 `try` 블록 **앞에서** 미리 선언해 둔 것입니다. 언뜻 보면 불필요해 보이지만, 이 한 줄이 없으면 미묘한 버그가 생길 수 있습니다. `try` 블록 안에서 `game = QuizGame()`이 실행되기도 전에, 즉 `QuizGame()` 생성자 자체가 실행되는 도중에 `Ctrl+C`가 눌리면 어떻게 될까요? 이 경우 `game`이라는 이름에는 아직 아무 값도 대입되지 않았을 것입니다. 만약 `try` 앞에서 `game`을 선언해 두지 않았다면, `except` 블록의 `if game is not None:` 검사 자체가 `NameError: name 'game' is not defined`로 실패하게 됩니다. 예외를 안전하게 처리하려던 코드가 오히려 새로운 예외를 만들어내는 셈입니다. `try` 앞에서 `None`으로 미리 선언해 두면, `QuizGame()` 생성 중에 예외가 나든 `game.run()` 도중에 예외가 나든 상관없이 `game`이라는 이름은 항상 존재하고, `if game is not None:`이 "생성까지는 성공했는지"를 안전하게 판단할 수 있습니다.

### 반복되는 패턴: 두 except 블록

`except KeyboardInterrupt`와 `except EOFError` 두 블록을 나란히 놓고 보면 구조가 거의 동일합니다. ① 상황에 맞는 안내 메시지를 `print`로 출력하고, ② `game`이 생성되어 있으면 `_save_before_exit(game)`을 호출하는 두 단계로 이루어져 있습니다. `_save_before_exit` 함수는 `game.save_state()`의 반환값(`bool`)을 보고 메시지를 다르게 출력합니다. `save_state()`가 `True`를 돌려주면 "💾 현재 데이터를 저장하고 종료합니다."를, 저장이 실패해 `False`를 돌려주면 "⚠️ 데이터를 저장하지 못했지만 프로그램을 종료합니다."를 출력합니다. 즉 저장이 실패하더라도 프로그램은 무리하게 재시도하지 않고 깔끔하게 종료를 이어갑니다. 이렇게 공통 로직을 별도 함수로 뽑아 두었기 때문에, 두 예외 처리 블록은 "어떤 메시지를 먼저 보여줄지"만 다르고 나머지는 코드 중복 없이 재사용됩니다.

### echo "" 파이프와 실제 Ctrl+D의 미묘한 차이

체크리스트는 "`echo "" | python main.py` 또는 Python 3에 맞는 명령으로 EOF 종료를 직접 시험"하라고 요구합니다. 실제로 `echo "" | python3 main.py`를 실행해 보면 다음과 같은 출력을 확인할 수 있습니다.

```
========================================
선택: ⚠️ 입력이 비어 있습니다. 다시 입력하세요.
선택: 
⚠️ 입력 스트림이 종료되었습니다. (EOF)
💾 현재 데이터를 저장하고 종료합니다.
```

여기서 흥미로운 점은 EOF 메시지가 나오기 전에 "입력이 비어 있습니다"라는 경고가 한 번 먼저 나온다는 것입니다. `echo ""`는 개행 문자 하나짜리 빈 줄을 파이프로 보내기 때문에, 첫 번째 `input()` 호출은 빈 문자열을 정상적으로 읽어 들이고, `ask_int` 안의 "입력이 비어 있으면 다시 물어본다" 분기를 한 번 타게 됩니다. 그다음 두 번째 `input()`을 호출할 때는 파이프에 더 이상 보낼 데이터가 없으므로 그제서야 `EOFError`가 발생합니다.

반면 사용자가 실제 터미널에서 `python3 main.py`를 실행한 뒤 프롬프트가 뜨자마자 아무 것도 입력하지 않고 곧바로 `Ctrl+D`를 누른 로그를 보면 다음과 같습니다.

```
선택: 
⚠️ 입력 스트림이 종료되었습니다. (EOF)
```

이 경우는 "입력이 비어 있습니다" 경고 없이 곧장 EOF 처리로 넘어갑니다. `Ctrl+D`는 (아직 아무 문자도 입력하지 않은 줄에서 누르면) 개행 문자조차 보내지 않고 표준 입력을 즉시 닫아버리기 때문에, 첫 번째 `input()` 호출 자체가 빈 문자열이 아니라 `EOFError`로 곧바로 실패합니다. 즉 `echo "" | python3 main.py`와 실제 터미널의 `Ctrl+D`는 "결국 EOFError로 종료된다"는 같은 목적지에 도달하지만, 그 사이에 빈 입력 경고를 한 번 거치느냐 아니냐라는 경로 차이가 있습니다. 이 차이는 버그가 아니라 `echo`가 개행 문자를 하나 흘려보낸다는 셸의 동작 차이에서 비롯된 자연스러운 결과이며, 두 경로 모두 `main()`의 `except EOFError` 블록으로 안전하게 수렴한다는 점이 중요합니다.

### 왜 이 방식이 안전한가: 예외를 뭉뚱그리지 않는다

`main()`의 `try` 블록은 `except KeyboardInterrupt`와 `except EOFError` 딱 두 종류만 좁게 잡습니다. `except Exception`이나 맨몸 `except:`처럼 모든 예외를 한꺼번에 삼키지 않습니다. 이는 의도적인 설계입니다. 만약 코드에 버그가 있어서 `game.run()` 내부에서 예상치 못한 `TypeError`나 `AttributeError`가 발생한다면, 이 예외는 `KeyboardInterrupt`도 `EOFError`도 아니므로 `main()`의 `try/except`에 걸리지 않고 그대로 위로 전파되어 원래대로 Traceback을 출력하며 프로그램이 종료됩니다. 언뜻 "예외를 다 잡아서 조용히 넘어가는 게 더 안전해 보이지 않나?"라고 생각할 수 있지만, 실제로는 정반대입니다. 코드 버그로 인한 예외까지 조용히 삼켜버리면 프로그램이 어디서 왜 잘못됐는지 알 방법이 없어지고, 디버깅이 훨씬 어려워집니다. 반면 지금처럼 "사용자가 의도적으로 종료를 요청한 경우"에 해당하는 두 예외만 좁게 처리하면, 정상적인 종료 요청은 친절하게 안내하면서도 진짜 버그는 Traceback을 통해 즉시 드러나므로 개발 중에 놓치지 않을 수 있습니다.

### 흔한 실수와 주의사항

- `try` 블록 밖, 혹은 `try` 안 첫 줄이 아닌 곳에서 `game`을 선언하면 `NameError`가 발생할 수 있는 경로가 생깁니다. `game: QuizGame | None = None`은 반드시 `try` 진입 전에 있어야 합니다.
- `ask_int`, `ask_text` 같은 하위 입력 함수 안에서 `KeyboardInterrupt`나 `EOFError`를 함부로 잡아버리면, 그 예외가 `main()`까지 전달되지 않아 최상위 안전 종료 로직이 아예 작동하지 않게 됩니다. 실제로 `main.py`의 `ask_int` 문서 주석에도 "ValueError만 처리하여 KeyboardInterrupt와 EOFError는 상위 실행 흐름에서 안전하게 처리할 수 있도록 그대로 전달한다"고 명시되어 있는데, 이는 이 설계를 지키기 위한 의도적인 장치입니다.
- EOF 테스트를 할 때 `echo ""`와 실제 `Ctrl+D`가 항상 동일한 경로를 타는 것은 아니라는 점을 기억해 두어야 합니다. 자동화된 테스트 스크립트에서 `echo ""`만 확인하고 "EOF 처리가 끝났다"고 단정하면, 실제 사용자가 첫 프롬프트에서 바로 `Ctrl+D`를 누르는 경로는 놓칠 수 있습니다. 가능하다면 두 경로를 모두 눈으로 확인하는 것이 좋습니다.

## 3-5. 입력 예외 9종 실습과 Git 체크포인트

메뉴 골격과 `ask_int`/`ask_text` 같은 공통 입력 검증 헬퍼를 만들었다면, 그다음 할 일은 "정상적인 경우"만이 아니라 "사용자가 실수하거나 프로그램을 강제로 끊는 경우"까지 직접 눌러보면서 확인하는 것입니다. 코드를 읽는 것과 실제로 터미널에 앉아서 abc를 쳐보고 Ctrl+C를 눌러보는 것은 완전히 다른 확인입니다. 이 절에서는 실제로 실행해서 얻은 로그를 근거로, 체크리스트의 입력 예외 9종이 각각 어떤 메시지로 이어졌는지 표로 정리합니다.

### 입력 예외 9종, 실제로 어떤 메시지가 나왔나

| # | 체크리스트 항목 | 실제 입력 | 실제로 이어진 메시지 | 근거 |
|---|---|---|---|---|
| 1 | 메뉴 1~5 각각 정상 분기 | `1`~`5` 순서대로 입력 | 1~4는 각각 "🚧 [기능명] 기능 준비 중입니다.", 5는 "👋 프로그램을 종료합니다. 이용해 주셔서 감사합니다!" 출력 후 정상 종료 | 실제 터미널 로그(첫 번째 실행) |
| 2 | 앞뒤 공백이 있는 메뉴 입력 | 예: `" 1 "` | 로그에 직접 등장하지 않음 | 로그 없음 — 아래 설명 참고 |
| 3 | abc 입력 | `abc` | "⚠️ 숫자를 입력하세요." | 실제 터미널 로그 |
| 4 | 9 입력 | `9` | "⚠️ 1~5 사이의 숫자를 입력하세요." | 실제 터미널 로그 |
| 5 | 0, -1 입력 | `0`, `-1` | 둘 다 동일하게 "⚠️ 1~5 사이의 숫자를 입력하세요." | 실제 터미널 로그 |
| 6 | Enter만 누른 빈 입력 | 빈 줄(파이프로 `echo ""` 전달) | "⚠️ 입력이 비어 있습니다. 다시 입력하세요." | `echo "" \| python3 main.py` 검증 결과 |
| 7 | 1.5 입력 | `1.5` | "⚠️ 숫자를 입력하세요." | 실제 터미널 로그 |
| 8 | Ctrl+C 안전 종료 | `^C` | "⚠️ 사용자에 의해 프로그램이 중단되었습니다. (Ctrl+C)" + "💾 현재 데이터를 저장하고 종료합니다." | 실제 터미널 로그 |
| 9 | EOF/파이프 입력 안전 종료 | 터미널에서 즉시 Ctrl+D | "⚠️ 입력 스트림이 종료되었습니다. (EOF)" + "💾 현재 데이터를 저장하고 종료합니다." | 실제 터미널 로그 |

정직하게 짚어야 할 부분이 두 가지 있습니다.

첫째, **2번 "공백이 있는 메뉴 입력"은 이 로그에 직접 등장하지 않습니다.** `main.py`의 `ask_int` 코드를 보면 `raw = input(prompt).strip()`으로 앞뒤 공백을 먼저 제거한 뒤 정수 변환을 시도하므로, `" 1 "`처럼 공백이 섞인 입력도 정상적으로 `1`로 처리될 것이 코드상으로는 보장됩니다. 다만 이건 코드를 읽고 추론한 것이지, 실제로 그 입력을 쳐서 로그로 확인한 것은 아직 아닙니다. "이론상 되어야 한다"와 "실제로 눌러서 확인했다"는 다른 얘기이므로, 나중에 시간이 나면 한 번은 직접 쳐보고 결과를 남겨두는 것이 좋습니다.

둘째, **6번과 9번은 미묘하게 얽혀 있습니다.** 사용자가 붙여넣은 로그의 두 번째 실행을 보면 `선택: ` 바로 다음 줄에 "입력이 비어 있습니다" 없이 곧장 "입력 스트림이 종료되었습니다 (EOF)"가 나옵니다. 이건 터미널에서 아무것도 입력하지 않은 채 Ctrl+D를 눌렀기 때문입니다 — `input()`이 빈 문자열을 반환하기도 전에 스트림 자체가 끊겨서 바로 `EOFError`가 발생합니다. 반면 `echo "" | python3 main.py`처럼 빈 줄 하나를 파이프로 흘려보내면, 그 줄은 일단 `input()`에 "빈 문자열"로 전달되어 `ask_int`의 "입력이 비어 있습니다" 분기를 먼저 타고, 그다음 `input()` 호출에서야 파이프가 닫혀 있어 EOF가 발생합니다. 즉 같은 "빈 입력처럼 보이는 상황"이라도 Enter를 눌렀는지, 아무 것도 안 누르고 스트림을 끊었는지에 따라 코드가 타는 경로가 다릅니다. 6번 항목의 메시지는 이 파이프 테스트로 확인한 것이고, 9번 항목의 메시지는 실제 터미널 로그로 확인한 것입니다.

7번(1.5 입력)이 abc와 같은 "숫자를 입력하세요" 메시지로 이어지는 이유도 짚어둘 만합니다. `int("1.5")`는 파이썬에서 `ValueError`를 던지기 때문에, 소수점이 있는 문자열은 정수 변환 실패로 처리되어 abc와 동일한 분기를 탑니다. `float`가 아니라 `int`로만 변환을 시도하는 `ask_int`의 설계상 자연스러운 동작입니다.

### Git 체크포인트: 사실은 커밋과 push가 이미 끝나 있습니다

체크리스트 3-5 섹션은 지금 `docs/learning_checklist.md`에서 커밋 #4, 커밋 #5, push, 스크린샷 항목까지 전부 `[ ]`로 남아 있습니다. 그런데 실제 `git log`를 찍어보면 이야기가 다릅니다.

```bash
$ git log --oneline --decorate
5ba64a0 (HEAD -> main, origin/main) Feat: QuizGame 클래스 골격 및 공통 입력 검증 헬퍼 구현 메인 루프 및 안전 종료 처리
6868c74 Feat: Quiz 클래스 구현 (문제 출력/정답 확인/딕셔너리 변환)
9d106fd Chore: 프로젝트 초기 설정 및 .gitignore 추가
...
```

`HEAD -> main`과 `origin/main`이 정확히 같은 커밋 `5ba64a0`을 가리키고 있습니다. 이는 로컬 커밋과 원격 push가 이미 끝나 있다는 뜻입니다. 체크박스가 비어 있다고 해서 작업이 안 된 것은 아니고, **체크리스트에 체크 표시를 남기는 절차만 아직 안 한 것**입니다. 이 둘을 구분해서 보는 습관이 중요합니다 — 체크박스는 실제 상태를 보여주는 게 아니라 "내가 상태를 기록했는지"를 보여줄 뿐입니다.

### 계획했던 커밋 2개가 다시 1개로 합쳐졌습니다

체크리스트는 원래 이 단계를 커밋 #4("QuizGame 클래스 골격 및 공통 입력 검증 헬퍼 구현")와 커밋 #5("메인 메뉴 루프 및 KeyboardInterrupt/EOFError 안전 종료 처리")로 나눠서 커밋하라고 안내했습니다. 그런데 실제 커밋 메시지를 보면 두 문장이 이어붙어 하나의 커밋이 되어 있습니다.

```
5ba64a0 Feat: QuizGame 클래스 골격 및 공통 입력 검증 헬퍼 구현 메인 루프 및 안전 종료 처리
```

`git show --stat 5ba64a0`으로 확인해 보면 이 한 커밋 안에 `main.py`, `quiz.py`(신규), `storage.py`, `README.md`, `docs/learning_checklist.md`, `docs/study/step0_dev_environment_git_init.md`(신규), `docs/study/step1_quiz_model.md`(신규), `docs/screenshots/step1_git.png`(신규)까지 8개 파일, 1187줄 추가/198줄 삭제가 한꺼번에 들어가 있습니다.

이 현상, 사실 처음이 아닙니다. Step 1 학습 노트(`docs/study/step1_quiz_model.md`)에서도 계획했던 커밋 2개가 실제로는 `6868c74` 하나로 합쳐진 사례가 있었습니다. 즉 `docs/learning_checklist.md` 맨 위의 "모든 기능 커밋에 적용할 공통 규율"이 경고했던 문제가 Step 1과 Step 2에 걸쳐 두 번 그대로 재현된 것입니다. 이걸 실패로 볼 필요는 없습니다. 오히려 같은 패턴이 두 번 반복되었다는 걸 알아차린 지금이, 이 패턴을 의식적으로 고칠 수 있는 가장 좋은 시점입니다.

다음에 시도해볼 만한 구체적인 방법 세 가지입니다.

- **(a) 메서드 하나를 완성할 때마다 바로 커밋하기.** `ask_int`를 다 짜고 나면 바로 `git add main.py && git commit`, `run()` 메서드를 완성하면 또 바로 커밋 — 이렇게 작은 단위로 끊으면 "나중에 한꺼번에 커밋하다가 합쳐지는" 상황 자체가 잘 생기지 않습니다.
- **(b) 커밋하기 전에 `git status`를 자주 확인하기.** `git add`를 치기 전에 `git status`로 지금 변경된 파일 범위가 내가 생각한 범위와 같은지 눈으로 먼저 확인하는 습관을 들이면, 의도치 않게 여러 작업이 섞여 스테이징되는 걸 미리 알아챌 수 있습니다.
- **(c) 이미 섞인 변경을 나누고 싶다면 `git add -p` 사용하기.** 한 파일 안에 서로 다른 목적의 변경이 뒤섞여 있을 때는 `git add -p`로 변경 덩어리(hunk)를 하나씩 보면서 원하는 부분만 골라 스테이징할 수 있습니다. `y`/`n`으로 훅 단위 선택, `s`로 훅을 더 잘게 쪼갤 수도 있습니다.

### 체크리스트에 아직 반영 안 된 것들

`docs/learning_checklist.md`를 diff해 보면, 3-1~3-4 섹션의 체크박스는 이번 커밋 `5ba64a0` 안에서 이미 `[ ]`에서 `[x]`로 바뀐 채로 코드와 같이 커밋되어 있습니다. 이전 Step들과 달리 이번에는 체크리스트 갱신을 코드 커밋과 같은 타이밍에 반영한 것으로, 좋은 진전입니다. 다만 3-5 섹션만은 아직 전부 `[ ]`로 남아 있는데, 위에서 확인했듯 커밋과 push 자체는 이미 끝났으니 체크 표시만 마저 갱신하면 됩니다.

마지막으로 `docs/screenshots/invalid_input.png`는 체크리스트에 "필요하면"이라는 조건이 붙은 선택 항목이고, 아직 만들어지지 않았습니다. 잘못된 입력 화면(abc, 9, 0, -1, 1.5 등)을 캡처해서 남겨두면 나중에 이 문서를 다시 볼 때 실제 화면을 함께 볼 수 있어 유용하지만, 지금 당장 필수는 아닙니다.

**참고**: Step 1 학습 노트가 지적했던 `storage.py`의 `from quiz import Quiz, get_default_quizzes` import 문제는 이번에 실제로 해결되었습니다. `quiz.py`(166줄)가 새로 생겨 `Quiz` 클래스와 `get_default_quizzes()`가 그 안으로 옮겨졌고, `python3 -c "import storage"`를 실행하면 에러 없이 "storage import OK"가 출력됩니다. 이전 단계에서 발견한 문제를 다음 단계에서 실제로 고쳤다는 것 — 이런 흐름이 쌓이는 게 코드가 나아지고 있다는 가장 확실한 신호입니다.
