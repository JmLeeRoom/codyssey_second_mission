## 1-1. Python·Git 개발 환경

### Python·Git 버전 확인

Python과 Git은 이 프로젝트가 돌아가는 최소한의 기반입니다. 버전이 맞지 않으면 이후 단계에서 사용할 문법(f-string, `pathlib`, 타입 힌트 등)이 아예 동작하지 않거나, `git branch -M`, `git config init.defaultBranch` 같은 비교적 최신 Git 옵션이 지원되지 않을 수 있습니다. 그래서 코드를 작성하기 전에 버전부터 확인하는 것이 첫 순서입니다.

```bash
python3 --version
git --version
```

이 프로젝트에서 실제로 확인한 값은 다음과 같습니다.

```
Python 3.12.3
git version 2.43.0
```

체크리스트가 요구하는 "Python 3.10 이상"을 3.12.3으로 충분히 만족하고, Git도 2.43.0으로 `init.defaultBranch` 같은 옵션을 지원하는 충분히 최신 버전입니다. 흔한 실수로는 `python`과 `python3`를 혼동하는 경우가 있습니다. macOS/Linux에서는 시스템 기본 `python`이 아예 없거나 Python 2를 가리키는 경우가 있으므로, 이 체크리스트는 명시적으로 `python3`을 기준으로 삼습니다.

### 커밋 작성자 정보: user.name / user.email

Git의 모든 커밋에는 "누가, 언제 이 변경을 만들었는가"라는 메타데이터가 함께 저장됩니다. 이 메타데이터의 핵심이 `user.name`과 `user.email`입니다. 설정하지 않고 커밋하면 Git이 임시로 컴퓨터 계정 이름 같은 값을 채우거나 아예 커밋을 거부하는데, 이렇게 만들어진 커밋은 나중에 `git log`나 GitHub에서 작성자를 알아볼 수 없어 협업 이력으로서 의미가 없어집니다. 특히 `user.email`은 GitHub가 커밋을 계정과 연결하는 기준이기도 해서, 저장소에 등록된 이메일과 다르면 커밋은 남아도 GitHub 프로필의 기여 잔디(contribution graph)나 아바타에 반영되지 않습니다.

```bash
git config --global user.name "내이름"
git config --global user.email "GitHub가입이메일"
```

이 프로젝트에서는 다음과 같이 설정했습니다.

```
user.name  = JmLeeRoom
user.email = togoda1945@gmail.com
```

`user.email`이 GitHub 가입 이메일(togoda1945@gmail.com)과 동일하므로, 이 저장소에 쌓인 커밋들은 모두 JmLeeRoom 계정의 기여로 정상 인식됩니다. 커밋 이후에 이름·이메일을 바꾸면 새 커밋부터만 적용되고 과거 커밋의 작성자 정보는 바뀌지 않는다는 점도 주의할 부분입니다. 과거 이력까지 고치려면 `git commit --amend`나 히스토리 재작성이 필요한데, 이는 이미 push된 커밋에서는 위험하므로 애초에 작업을 시작하기 전 정확한 값으로 설정해 두는 것이 안전합니다.

### 기본 브랜치 이름: init.defaultBranch

`init.defaultBranch`는 `git init`으로 새 저장소를 만들 때 첫 브랜치에 어떤 이름을 붙일지 정하는 설정입니다. 이 설정이 필요한 이유는 역사적 배경과 관련이 있습니다. Git은 2005년 만들어진 이후 오랫동안 첫 브랜치 이름을 `master`로 고정해 왔습니다. 그런데 2020년 무렵 업계 전반에서 master/slave 같은 용어를 대체하려는 움직임이 있었고, GitHub도 2020년 10월부터 새로 만드는 저장소의 기본 브랜치 이름을 `main`으로 바꾸었습니다. Git 자체는 하위 호환을 위해 여전히 `master`를 기본값으로 두되, `init.defaultBranch` 설정으로 사용자가 원하는 이름을 지정할 수 있게 했습니다.

```bash
git config --global init.defaultBranch main
```

이 설정을 해 두지 않으면 로컬에서 `git init`으로 만든 저장소는 `master` 브랜치로 시작하는데, GitHub에서 새로 만든 원격 저장소는 `main`을 기본으로 기대하기 때문에 `git push`ㆍ`git pull` 시 브랜치 이름 불일치로 혼란이 생길 수 있습니다. 이 프로젝트는 `init.defaultbranch = main`으로 설정해 두어, 이후 `git init`을 실행할 때마다 로컬 브랜치가 처음부터 `main`으로 만들어지도록 맞춰 두었습니다. 다만 이 설정은 앞으로 새로 생성하는 저장소에만 적용되며, 이미 `master`로 만들어진 기존 저장소의 브랜치 이름을 자동으로 바꿔 주지는 않는다는 점은 흔히 오해하는 부분입니다. 기존 저장소라면 `git branch -M main`으로 직접 이름을 바꿔야 합니다.

### git config의 3단계 설정 범위

`git config`는 설정이 적용되는 범위에 따라 세 단계로 나뉘고, 더 좁은 범위가 더 넓은 범위를 덮어씁니다.

| 범위 | 옵션 | 저장 위치 | 적용 대상 |
|---|---|---|---|
| 시스템 전체 | `--system` | `/etc/gitconfig` | 이 컴퓨터를 쓰는 모든 사용자, 모든 저장소 (관리자 권한 필요) |
| 사용자 전역 | `--global` | `~/.gitconfig` | 현재 로그인한 사용자가 다루는 모든 저장소 |
| 저장소 개별 | `--local` (기본값) | `<저장소>/.git/config` | 지금 작업 중인 이 저장소 하나만 |

`--global`은 "이 컴퓨터의 이 계정으로 만드는 모든 Git 저장소에 공통으로 적용"한다는 의미입니다. 그래서 `user.name`·`user.email`처럼 어느 프로젝트에서든 동일해야 하는 값은 한 번만 `--global`로 설정해 두면, 이후 만드는 모든 저장소에서 매번 다시 입력할 필요가 없습니다. 반대로 회사 프로젝트와 개인 프로젝트에서 이메일을 다르게 쓰고 싶다면, 해당 저장소 디렉터리 안에서 `--local`(옵션을 생략한 `git config user.email "..."`)로 그 저장소만의 값을 덮어쓰면 됩니다.

```bash
git config --global --list
```

이 프로젝트에서 확인한 결과에는 다음 값이 포함되어 있습니다.

```
user.name=JmLeeRoom
user.email=togoda1945@gmail.com
init.defaultbranch=main
```

세 값이 모두 `--global` 범위로 정상 등록되어 있어, 이 컴퓨터에서 만드는 다른 저장소에서도 같은 작성자 정보와 기본 브랜치 이름이 자동으로 적용됩니다. 흔한 실수는 `--global`을 빠뜨리고 그냥 `git config user.name "..."`만 실행하는 것인데, 이 경우 `--local`로 처리되어 현재 저장소에만 적용되고 다른 프로젝트에서는 다시 설정 안 된 상태로 남습니다.

### 환경 캡처와 저장 경로

체크리스트는 Python 버전, Git 버전, `git config --global --list` 결과가 한 화면에 보이도록 캡처해 두라고 요구합니다. 세 정보를 한 번에 모아 두면 나중에 "이 프로젝트를 어떤 환경에서 작업했는가"를 별도 설명 없이 스크린샷 한 장으로 증빙할 수 있기 때문입니다. 이 저장소에는 `docs/screenshots/git_setting.png`, `docs/screenshots/git_check_point.png` 캡처 파일이 실제로 존재하며, 체크리스트가 제시한 기본 경로인 `docs/screenshots/env_setup.png`와는 이름이 다릅니다. 이런 경우 체크리스트 항목이 안내한 대로 파일명을 억지로 맞추기보다, 실제 저장된 파일 경로와 README 등 문서에서 참조하는 경로·설명이 서로 일치하는지를 확인하는 것이 핵심입니다. 경로가 다르면 GitHub 웹에서 이미지가 깨진 링크로 표시되므로, 캡처 파일을 추가하거나 이름을 바꿀 때는 반드시 문서 내 이미지 링크도 함께 갱신해야 합니다.

## 1-2. 주제와 기본 문제 준비

### 왜 코드보다 문서를 먼저 쓰는가

퀴즈 프로그램을 만들 때 가장 먼저 할 일은 코드를 작성하는 것이 아니라 "무엇을 물어볼 것인가"를 문서로 확정하는 것입니다. `docs/learning_checklist.md`의 이 단계는 실제로 README.md의 "2. 퀴즈 주제와 선정 이유" 섹션과 "4. 기능 목록"에 들어갈 문제 데이터를 코드 작성 전에 먼저 확정해 두는 과정입니다. 이렇게 순서를 지키는 이유는 두 가지입니다.

첫째, 문제 문장·선택지·정답 번호가 먼저 고정되어야 `Quiz` 클래스가 다룰 데이터 구조(문제 1건 = 문자열 1개 + 선택지 리스트 4개 + 정답 정수 1개)를 명확히 설계할 수 있습니다. 둘째, 나중에 README를 읽는 사람(또는 채점하는 사람)이 "이 프로그램이 왜 이 주제를 다루는가"를 코드가 아니라 문서만 보고도 판단할 수 있어야 하기 때문입니다. 즉 이 체크리스트 항목들은 요구사항 문서(README)와 실제 실행 데이터(퀴즈 5문제)가 서로 어긋나지 않도록 미리 맞춰두는 작업입니다.

### 주제 확정: 자료구조(Data Structure)

체크리스트의 주제 선정 관련 3개 항목은 모두 완료된 상태이며, 실제로 다음과 같은 이유로 자료구조를 주제로 확정했습니다.

- **이유 1 — 정답이 명확함**: 스택은 LIFO, 큐는 FIFO처럼 "맞다/틀리다"가 논쟁의 여지 없이 갈리므로, 서술형이 아닌 4지선다 객관식 문제를 만들기에 적합합니다.
- **이유 2 — 프로그램 구현과의 연결**: 이 퀴즈 프로그램 자체가 `list`, `dict`, `json` 모듈로 문제 데이터와 `state.json`을 다루기 때문에, "자료구조"라는 학습 주제가 실제 코드에서 쓰는 자료구조와 자연스럽게 이어집니다.
- **이유 3 — CS 기초로서의 수명**: 스택·큐·해시 테이블·트리·시간 복잡도는 특정 언어나 프레임워크가 바뀌어도 계속 쓰이는 지식이라 학습 자료의 가치가 오래 유지됩니다.

### 기본 문제 5개 준비

각 문제는 "문제 문장 + 선택지 정확히 4개 + 정답 번호(1~4 중 하나)"라는 동일한 형식으로 미리 작성해 두었고, 실제 README.md에는 다음 5문제가 담겨 있습니다.

| 번호 | 문제 | 정답 번호 | 정답 내용 |
|---|---|---|---|
| 1 | 스택(Stack)의 자료 처리 방식은? | 2 | LIFO |
| 2 | 큐(Queue)의 자료 처리 방식은? | 1 | FIFO |
| 3 | 너비 우선 탐색(BFS)에서 주로 쓰는 자료구조는? | 2 | 큐 |
| 4 | 정렬된 배열에서 이진 탐색의 시간 복잡도는? | 2 | O(log n) |
| 5 | 해시 테이블의 평균 키 탐색 시간 복잡도는? | 3 | O(1) |

문제 1·2는 각각 스택의 LIFO, 큐의 FIFO를 검증하는 가장 기본적인 문제입니다. 문제 3은 "BFS는 큐를 사용한다"는 사실을 확인하는 문제이고, 문제 4는 정렬된 배열에서의 이진 탐색이 O(log n)이라는 점을, 문제 5는 해시 테이블의 평균 탐색이 O(1)이라는 점을 검증합니다. 코드에서는 이 표가 다음과 같은 `dict` 구조로 저장됩니다.

```python
quiz_data = [
    {
        "question": "큐(Queue)의 자료 처리 방식은?",
        "options": ["FIFO", "LIFO", "Random", "Priority"],
        "answer": 1,
    },
    # ... 나머지 4문제
]
```

### 흔한 실수: 선택지 순서와 answer 번호가 따로 노는 경우

가장 자주 발생하는 실수는 선택지 순서를 바꾸면서 `answer` 번호는 그대로 두는 것입니다. 큐 문제를 예로 들면, 실제 README에서는 `["FIFO", "LIFO", "Random", "Priority"]` 순서로 FIFO가 1번이기 때문에 정답은 `1`입니다. 그런데 만약 나중에 선택지 순서를 `["LIFO", "FIFO", "Random", "Priority"]`처럼 바꿔서 FIFO가 2번으로 이동했다면, `answer` 값도 반드시 `1`에서 `2`로 함께 바뀌어야 합니다. 그렇지 않으면 실제로는 FIFO가 정답인데 프로그램은 LIFO를 정답으로 채점하는 버그가 생깁니다.

그래서 체크리스트 마지막 항목처럼, 선택지를 수정할 때마다 "정답 문자열이 몇 번째 위치에 있는가"를 다시 세어서 `answer` 값을 갱신했는지 확인하는 절차가 반드시 필요합니다. 이 프로젝트에서는 스택 문제(LIFO=2번)와 큐 문제(FIFO=1번)의 정답 번호가 서로 다르다는 점 자체가, 선택지 순서와 정답 번호를 문제마다 개별적으로 맞춰 작성했다는 근거이기도 합니다.

## 1-3. GitHub·로컬 저장소

### 지금까지 완료된 부분

체크리스트를 보면 이 섹션의 항목 중 절반 정도는 이미 `[x]`로 표시되어 있습니다. 먼저 이 부분부터 실제 근거와 함께 정리합니다.

| 항목 | 상태 | 근거 |
|---|---|---|
| GitHub 새 저장소 생성 · Public 설정 | 완료 | `git remote -v`에 `codyssey_second_mission` 저장소 URL 존재 |
| `git status`로 작업 트리 확인 | 완료 | 아래 예시 참고 |
| `git remote add origin` 실행 | 완료 | origin이 이미 연결됨 |
| `git remote -v`로 URL 확인 | 완료 | 아래 값 참고 |
| `git pull --rebase origin main` 실행 | 완료 | 체크리스트상 완료 표시 |

원격 저장소는 다음과 같이 연결되어 있습니다.

```bash
$ git remote -v
origin  https://github.com/JmLeeRoom/codyssey_second_mission.git (fetch)
origin  https://github.com/JmLeeRoom/codyssey_second_mission.git (push)
```

fetch와 push 주소가 동일하게 `JmLeeRoom/codyssey_second_mission.git`을 가리키고 있으므로, 원격 저장소 연결 자체는 정상입니다. `git status`를 실행하면 현재 작업 트리 상태를 다음처럼 확인할 수 있습니다.

```bash
$ git status
On branch main
Changes not staged for commit:
        modified:   docs/learning_checklist.md
Untracked files:
        docs/screenshots/git_check_point.png
        docs/screenshots/git_setting.png
        quiz.py
        storage.py
```

`M`(수정)과 `??`(추적되지 않음)이 섞여 있는 상태로, 아직 `git add`로 스테이징하지 않은 변경 사항이 있다는 뜻입니다. `git status`는 커밋 전에 항상 먼저 실행해서 "내가 지금 무엇을 커밋하려는지" 눈으로 확인하는 습관을 들이는 것이 중요합니다.

`git pull --rebase origin main`이 완료로 표시되어 있다는 것은, GitHub에 README가 이미 존재하는 상태에서 원격 커밋을 로컬 히스토리 앞쪽으로 재배치하는 작업까지 마쳤다는 의미입니다. 실제로 `git log --oneline`(오래된 순)을 보면 가장 오래된 커밋이 `d6877a1 first commit`으로, GitHub에서 저장소를 만들 때 자동 생성되는 커밋 이름과 유사한 형태를 보입니다. 다만 이것만으로 "Add a README file"을 실제로 체크했었는지 단정할 수는 없으므로, 이 부분은 다음 섹션에서 별도로 짚습니다.

### 아직 완료되지 않은 부분 — 직접 실습이 필요합니다

여기서부터는 체크리스트에 `[ ]`로 남아 있는 항목입니다. 저장소에 이미 커밋 7개가 쌓여 있고 origin도 연결되어 있지만, **그것이 곧 이 항목들을 실습하고 확인했다는 뜻은 아닙니다.** 체크리스트는 "결과물이 존재하는가"가 아니라 "그 명령어를 직접 실행해서 의미를 이해했는가"를 확인하는 절차이므로, 아래 항목들은 지금부터 손으로 직접 실행해 보시기 바랍니다.

**`git init`과 `git branch -M main`**

```bash
$ git init
$ git branch -M main
```

이미 `.git` 디렉터리가 있는 저장소에서 `git init`을 다시 실행해도 기존 커밋 히스토리가 지워지지 않습니다. Git은 이미 초기화된 저장소를 감지하면 `Reinitialized existing Git repository`라는 메시지만 출력하고 넘어갑니다. 마찬가지로 `git branch -M main`도 현재 브랜치 이름이 이미 `main`이라면 이름만 다시 확인하는 셈이라 안전합니다. `git config --global init.defaultbranch`가 `main`으로 설정되어 있어 새로 만드는 브랜치는 기본적으로 `main`이 되지만, 예전에 `master`로 시작한 저장소를 이어받았을 경우에는 이 명령어로 이름을 강제로 맞춰야 합니다. 지금 이 프로젝트에서 명령어를 직접 실행해 결과를 눈으로 확인한 뒤 체크 표시를 완료하시기 바랍니다.

**"Add a README file"을 선택하지 않는 이유**

GitHub에서 새 저장소를 만들 때 "Add a README file"에 체크하면, 원격 저장소에 `README.md` 하나만 있는 커밋(보통 `Initial commit` 또는 `first commit`)이 자동으로 생성됩니다. 그런데 로컬에도 이미 `git init` 후 커밋한 `README.md`가 있다면, 로컬과 원격 양쪽에 **같은 파일 이름이지만 서로 다른 이력(공통 조상 커밋이 없는 두 히스토리)** 으로 존재하게 됩니다. 이 상태에서 push나 rebase를 시도하면 Git은 "이 README.md를 어느 쪽 걸로 남겨야 할지" 판단하지 못해 충돌을 일으킵니다. 이번 저장소는 이미 만들어졌으므로 지금 되돌릴 수는 없지만, GitHub 저장소 페이지에서 첫 커밋 이력을 확인해 실제로 README가 자동 생성됐었는지 점검해 보고, **다음에 새 저장소를 만들 때는 이 옵션을 반드시 꺼 둔다**는 습관을 만드는 것이 이 항목의 핵심입니다.

**add/add 충돌이 발생하는 흐름**

```
[로컬]  d6877a1(first commit, README.md 버전A) → 40582bc → ... → 9d106fd
[원격]  a1b2c3d(Initial commit, README.md 버전B)

$ git pull --rebase origin main
 1) 원격의 a1b2c3d를 로컬 히스토리 맨 앞으로 가져와 재생(replay)
 2) 로컬의 d6877a1을 그 위에 다시 적용하려는 순간
    → 같은 경로(README.md)를 두 커밋이 각각 "새로 추가"하려 함
    → CONFLICT (add/add): Merge conflict in README.md
 3) rebase가 그 커밋에서 일시 정지되고, 사용자의 해결을 기다림
```

이때 `README.md`를 열어 보면 다음과 같은 표시가 남아 있습니다.

```text
<<<<<<< HEAD
(원격 버전 README 내용)
=======
(로컬 버전 README 내용)
>>>>>>> d6877a1 (first commit)
```

**충돌 해결 절차**

1. `<<<<<<<`, `=======`, `>>>>>>>` 표시를 모두 지우고, 실제로 남길 내용만 정리합니다. 이 프로젝트의 README에는 "1. 프로젝트 개요"부터 "6. 데이터 파일: state.json"까지 6개 필수 섹션이 있으므로, 두 버전 중 이 구조를 갖춘 쪽(또는 병합한 내용)을 남기면 됩니다.
2. 편집이 끝나면 아래 순서로 진행합니다.

```bash
$ git add README.md
$ git rebase --continue
$ git push -u origin main
```

`git add`는 "이 파일의 충돌을 해결했다"고 Git에 알리는 신호이고, `git rebase --continue`는 멈춰 있던 재생 작업을 다음 커밋으로 이어가라는 명령입니다. 마지막에 `-u` 옵션으로 push하면 이후부터는 `git push`만으로 `origin/main`을 추적합니다.

**`git rebase --abort`는 언제 쓰나**

rebase 도중 충돌이 여러 커밋에 걸쳐 연쇄적으로 발생하거나, 어떤 내용을 남겨야 할지 확신이 서지 않을 때는 무리하게 진행하지 말고 아래 명령으로 되돌립니다.

```bash
$ git rebase --abort
```

이 명령은 rebase를 시작하기 이전 상태로 로컬 브랜치를 완전히 원상 복구합니다. `--continue`가 "충돌을 해결하고 앞으로 나아가는" 명령이라면, `--abort`는 "일단 멈추고 처음부터 원인을 다시 살펴보는" 명령입니다. 되돌린 뒤에는 `git status`와 `git log --oneline`으로 현재 상태를 다시 확인하고, 왜 충돌이 났는지(예: README를 두 곳에서 각각 만들었는지) 원인을 파악한 후 다시 시도하는 것이 안전합니다.

## 1-4. .gitignore와 README 초안

### .gitignore가 필요한 이유

Git 저장소를 초기화하고 나면(`git init`), 그 디렉터리 안에서 생성되는 모든 파일이 잠재적으로 커밋 대상이 됩니다. 하지만 실제로 버전 관리를 해야 하는 것은 "사람이 직접 작성한 소스 코드"뿐이고, 프로그램을 실행하는 과정에서 자동으로 생성되는 파일, 개발 환경에 따라 달라지는 설정 파일, 운영체제가 알아서 만드는 파일까지 모두 커밋해버리면 저장소가 지저분해지고 협업 시 불필요한 충돌이 생깁니다. `.gitignore`는 이런 파일들을 Git의 추적 대상에서 처음부터 제외시키는 명단입니다.

이 프로젝트에서는 저장소 루트에 `.gitignore` 파일을 생성했고, 다음 내용을 실제로 담고 있습니다.

```bash
# .gitignore 전체 내용 확인
cat .gitignore
```

```gitignore
# Python cache and bytecode
__pycache__/
*.py[cod]

# Virtual environments
.venv/
venv/

# Editor settings
.vscode/
.idea/

# Operating system files
.DS_Store
Thumbs.db

# Runtime quiz data
state.json
state.json.bak
```

파일이 잘 적용되고 있는지는 아래 명령어로 확인할 수 있습니다. 이미 추적 제외 대상으로 잡힌 파일에 대해서는 어떤 규칙에 걸렸는지 알려줍니다.

```bash
git check-ignore -v state.json
# .gitignore:15:state.json    state.json
```

### 카테고리별로 왜 무시해야 하는가

| 카테고리 | 패턴 | 무시하는 이유 |
|---|---|---|
| 캐시/바이트코드 | `__pycache__/`, `*.py[cod]` | 파이썬 인터프리터가 `.py` 파일을 실행할 때 컴파일된 바이트코드(`.pyc`)를 자동 생성합니다. 소스 코드에서 100% 재생성 가능하고, 실행 환경(파이썬 버전, OS)마다 내용이 달라지므로 커밋할 이유가 없습니다. |
| 가상환경 | `.venv/`, `venv/` | 가상환경 폴더에는 설치된 패키지 전체가 실제 바이너리로 들어 있어 용량이 크고, `requirements.txt` 같은 목록 파일로 언제든 재현할 수 있습니다. 사람마다 절대 경로가 다르게 박혀 있어 그대로 커밋하면 다른 컴퓨터에서 동작하지 않을 수도 있습니다. |
| 에디터 설정 | `.vscode/`, `.idea/` | VS Code, IntelliJ/PyCharm 등 에디터가 프로젝트별로 생성하는 개인 설정(테마, 브레이크포인트, 창 배치 등)입니다. 협업자마다 사용하는 에디터와 취향이 다르므로 공유 저장소에 강제할 필요가 없습니다. |
| 운영체제 파일 | `.DS_Store`, `Thumbs.db` | macOS의 Finder, Windows의 탐색기가 폴더를 열람할 때 자동으로 남기는 썸네일/메타데이터 캐시 파일입니다. 프로젝트 내용과 전혀 관계가 없고 OS가 다르면 아예 생성되지도 않습니다. |
| 런타임 데이터 | `state.json`, `state.json.bak` | 퀴즈를 풀 때마다 점수와 진행 상태가 바뀌어 기록되는 파일과 그 손상 대비 백업본입니다. 실행할 때마다 내용이 달라지므로 커밋하면 "코드 변경"이 아니라 "내가 퀴즈를 몇 번 풀었는지"가 이력에 쌓이게 됩니다. |

여기서 자주 하는 실수는, `.gitignore`에 패턴을 추가하기 **전에** 이미 `git add`로 추적을 시작해버린 파일이 있는 경우입니다. `.gitignore`는 "아직 추적되지 않은 파일"에만 적용되므로, 이미 추적 중인 파일은 목록에 넣어도 계속 변경 사항이 감지됩니다. 이런 경우에는 `git rm --cached 파일명`으로 추적만 해제한 뒤 커밋해야 합니다. 이 프로젝트는 `state.json`이 추적된 적 없이 처음부터 무시 목록에 있었기 때문에 이 문제는 겪지 않았습니다.

### 코드보다 README 제목부터 먼저 잡는 이유

README 초안 작업에서는 본문 내용을 채우기 전에, 먼저 6개의 섹션 제목만 빈 틀로 만들어두었습니다. 실제로 이 프로젝트의 README.md에는 다음 제목이 순서대로 들어 있습니다.

```markdown
## 1. 프로젝트 개요
## 2. 퀴즈 주제와 선정 이유
## 3. 실행 방법
## 4. 기능 목록
## 5. 파일 구조와 클래스 설계
## 6. 데이터 파일: state.json
```

코드를 한 줄도 짜기 전에 이 목차부터 확정하는 것은 단순한 형식이 아니라 하나의 설계 습관입니다. 제목 하나하나가 "이 프로젝트가 답해야 할 질문"을 뜻하기 때문입니다. 예를 들어 "6. 데이터 파일: state.json"이라는 제목을 미리 박아두면, 프로그램을 다 만들고 나서야 "실행 데이터를 어떻게 다룰지" 뒤늦게 고민하는 대신, 개발을 시작하는 시점부터 "이 파일을 커밋할지 말지, 그 이유를 어떻게 설명할지"를 의식하며 코드를 짜게 됩니다. 즉 목차를 요구사항 명세서처럼 미리 확정해두면, 나중에 README를 채워 넣을 때 무엇을 써야 할지 헤매지 않고, 반대로 지금 만드는 기능이 어느 섹션에 속하는지도 명확해집니다. 협업 관점에서도, 제목만 있는 빈 README라도 커밋해두면 동료나 미래의 자신이 "이 프로젝트에서 다뤄야 할 항목이 무엇인지"를 코드를 읽지 않고도 파악할 수 있습니다.

### state.json 추적 제외 결정과 README에 남긴 이유

이 프로젝트는 `state.json`을 Git 추적에서 제외하는 쪽을 선택했고, 그 이유를 README의 "6. 데이터 파일: state.json" 섹션에 실제로 기록해두었습니다. 핵심 근거는, 퀴즈를 풀 때마다 개인의 점수와 진행 상태가 담긴 `state.json`의 내용이 바뀌는데, 이걸 그대로 커밋하면 커밋마다 "코드가 왜 바뀌었는지"와 무관한 데이터 변경 이력이 쌓여 Git 히스토리가 오염된다는 점입니다. 소스 코드의 변경 이력을 살펴봐야 할 때 실행 결과 파일의 diff가 섞여 있으면 리뷰나 추적이 훨씬 번거로워집니다. 그래서 `state.json`과 그 백업본 `state.json.bak`을 처음부터 `.gitignore`에 등록해 커밋 대상에서 완전히 제외했습니다.

### 아직 완료되지 않은 항목: "state.json을 추적하기로 했다면"

체크리스트의 다음 항목은 이 프로젝트에서는 **완료된 항목이 아니라 해당 사항이 없는(N/A) 항목**입니다.

```markdown
- [ ] state.json을 의도적으로 Git 추적할 선택을 했다면, 동적 실행 데이터가
      커밋마다 바뀐다는 단점과 선택 이유를 README에 명시
      (이 프로젝트는 추적 제외를 선택했으므로 해당 없음)
```

이 프로젝트는 위에서 설명한 대로 `state.json`을 추적 제외하기로 결정했기 때문에, 이 항목이 요구하는 "추적하기로 했을 때의 문서화"는 실제로 수행할 필요가 없습니다. 다만 학습 목적으로, 만약 반대 선택(추적 포함)을 했다면 어떤 절차를 밟았어야 하는지 직접 실습해볼 수 있습니다.

```bash
# 1) .gitignore에서 state.json 관련 줄을 지운다
# 2) 강제로 추적을 시작한다
git add state.json
git commit -m "docs: state.json을 의도적으로 추적 (진행 상태 이력 보존 목적)"

# 3) README에 아래와 같은 내용을 명시했어야 한다
```

```markdown
## 6. 데이터 파일: state.json

본 프로젝트는 state.json을 의도적으로 Git 추적에 포함했습니다.
- 단점: 퀴즈를 풀 때마다 파일 내용이 바뀌어 커밋마다 diff가 발생하며,
  코드 변경과 무관한 이력이 쌓입니다.
- 선택 이유: (예시) 특정 시점의 진행 상태를 되돌리거나 비교할 필요가
  있어 이력 자체를 보존하기로 결정했습니다.
```

이렇게 두 갈래 선택지를 비교해보면, "제외"와 "포함" 중 어느 쪽을 고르든 정답은 없지만 반드시 그 이유를 README에 명시적으로 남겨야 한다는 원칙만은 공통이라는 점을 이해할 수 있습니다. 이 프로젝트는 전자를 택했고, 그 근거를 이미 README에 기록해 두었습니다.

## 1-5. 첫 번째 Git 체크포인트

지금까지 `.gitignore`를 작성하고 README.md의 골격을 잡았다면, 이제 이 파일들을 실제로 원격 저장소에 올려서 "체크포인트"를 만들 차례입니다. 이 섹션의 4가지 항목은 모두 완료된 상태이며, 아래에서는 각 명령어가 왜 그렇게 동작하는지, 그리고 이 프로젝트의 실제 결과가 무엇인지 확인합니다.

### git add .gitignore README.md — 파일을 콕 집어 스테이징하기

`git add`는 작업 디렉터리의 변경 사항을 커밋 후보(스테이징 영역)에 올리는 명령입니다. 이때 `git add -A`나 `git add .`처럼 디렉터리 전체를 한 번에 올리는 대신, 이 프로젝트에서는 파일명을 직접 지정했습니다.

```bash
git add .gitignore README.md
git status
```

이렇게 파일을 명시하는 방식이 더 안전한 이유는 두 가지입니다. 첫째, `git add -A`는 작업 디렉터리에 있는 **모든** 변경/추가 파일을 무조건 포함시키기 때문에, 아직 `.gitignore`에 등록되지 않은 임시 파일이나 개인 설정 파일이 실수로 커밋에 섞여 들어갈 위험이 있습니다. 둘째, 초기 설정 단계에서는 "지금 이 커밋에 정확히 무엇이 들어가야 하는가"를 스스로 검증하는 습관이 중요한데, 파일을 하나씩 지정하면 `git status`로 최종 확인했을 때 의도한 파일 목록과 실제 스테이징된 목록이 정확히 일치하는지 대조하기 쉽습니다. 실제로 이 프로젝트의 `.gitignore`에는 `__pycache__/`, `.venv/`, `state.json` 같은 항목이 이미 등록되어 있어 `git add -A`를 쓰더라도 결과가 크게 다르지 않았겠지만, 초기 커밋처럼 "이 저장소의 첫인상"이 되는 커밋일수록 명시적으로 무엇을 넣을지 통제하는 습관을 들이는 것이 좋습니다.

흔한 실수는 `git add .`을 습관적으로 쓰다가 `.env`나 API 키가 담긴 파일, 혹은 대용량 가상환경 폴더까지 커밋에 포함시키는 경우입니다. 파일을 지정해서 add하는 습관은 이런 사고를 원천적으로 줄여줍니다.

### git commit -m "Chore: ..." — 접두사로 커밋의 성격 표시하기

커밋 메시지 앞에 `Chore:`, `Feat:`, `Fix:` 같은 접두사를 붙이는 방식은 Conventional Commits라는 관례에서 온 것으로, 이 커밋이 어떤 종류의 변경인지 로그만 보고도 파악할 수 있게 해줍니다. `Chore`는 "잡일"이라는 뜻 그대로, 기능 로직(코드 동작)을 바꾸는 것이 아니라 프로젝트를 구동하기 위한 **부수적인 설정**(빌드 설정, `.gitignore`, 문서 초안 등)을 다룰 때 사용합니다.

```bash
git commit -m "Chore: 프로젝트 초기 설정 및 .gitignore 추가"
```

이 프로젝트의 `git log --oneline` 결과에는 이 커밋이 실제로 다음과 같이 남아 있습니다(최신순).

```
6868c74 Feat: Quiz 클래스 구현 (문제 출력/정답 확인/딕셔너리 변환)
9d106fd Chore: 프로젝트 초기 설정 및 .gitignore 추가
001a6ff settingfinish
ee25482 수정
b25c749 update README.md
40582bc test
d6877a1 first commit
```

`6868c74`가 `Feat:`로 시작하는 것과 비교해 보면 접두사의 의미가 더 뚜렷해집니다. `Feat`는 Quiz 클래스라는 실제 기능이 추가된 커밋이고, `Chore`는 그 기능이 동작하기 위한 배경 정리(캐시/가상환경 무시 설정, 문서 뼈대) 커밋입니다. 참고로 이 저장소에는 `9d106fd` 이전에도 `first commit`, `test`, `수정`, `settingfinish` 같은 초기 실습 커밋들이 이미 남아 있어, "첫 번째 체크포인트"라는 표현이 저장소의 진짜 첫 커밋을 의미하는 것은 아니라는 점도 함께 알아두면 좋습니다. 흔한 실수는 접두사를 붙이되 그 뒤 설명 없이 `Chore: 수정`처럼 모호하게 쓰는 것인데, 나중에 로그만 보고 무엇이 바뀌었는지 알 수 없게 됩니다.

### git push -u origin main — 원격 저장소와 연결하고 업로드하기

`git push`는 로컬 커밋을 원격 저장소로 전송하는 명령이고, `-u`(`--set-upstream`)는 현재 로컬 브랜치(`main`)와 원격 브랜치(`origin/main`) 사이에 **추적 관계(upstream)**를 등록하는 옵션입니다.

```bash
git push -u origin main
```

이 프로젝트의 `git remote -v` 결과는 다음과 같습니다.

```
origin  https://github.com/JmLeeRoom/codyssey_second_mission.git (fetch)
origin  https://github.com/JmLeeRoom/codyssey_second_mission.git (push)
```

`-u` 플래그를 한 번 사용해 두면, Git은 이후부터 "이 로컬 `main`은 `origin`의 `main`과 짝지어져 있다"는 것을 기억합니다. 그 덕분에 다음 커밋부터는 `git push origin main`처럼 인자를 전부 쓰지 않고 그냥 `git push`만 입력해도 되고, 반대로 원격의 변경 사항을 받아올 때도 `git pull`만으로 동작합니다. 만약 `-u` 없이 push했다면 매번 `origin main`을 직접 지정해야 하고, `git status`에서도 "이 브랜치가 원격의 어떤 브랜치와 비교해서 몇 커밋 앞서 있는지" 같은 정보가 표시되지 않습니다.

흔한 실수는 원격 저장소를 GitHub에서 먼저 README 자동 생성 옵션과 함께 만든 뒤 로컬에서 `git push -u origin main`을 시도해 "non-fast-forward" 오류를 만나는 경우입니다. 이 경우 초심자는 `git push --force`로 강제 덮어쓰기를 시도하기 쉬운데, 이는 원격의 커밋 이력을 통째로 날려버릴 수 있어 지양해야 합니다.

### GitHub 웹 페이지에서 결과 확인하기

마지막으로 로컬에서의 작업이 실제로 원격에 반영되었는지 브라우저로 직접 확인하는 절차입니다. `https://github.com/JmLeeRoom/codyssey_second_mission` 저장소 페이지에 접속해서 다음을 확인합니다.

- 파일 목록에 `.gitignore`와 `README.md`가 보이는지
- Commits 탭(또는 커밋 개수 링크)을 눌렀을 때 `Chore: 프로젝트 초기 설정 및 .gitignore 추가`(해시 `9d106fd`) 커밋이 이력에 존재하는지
- 커밋 작성자 정보가 `git config --global user.name`(`JmLeeRoom`), `user.email`(`togoda1945@gmail.com`)로 설정한 값과 일치하는지

로컬 `git log`는 내 컴퓨터 안의 이력일 뿐이므로, 이 웹 확인 단계를 거쳐야만 "push가 실제로 성공했다"는 것을 신뢰할 수 있습니다. 흔한 실수는 push 명령이 에러 없이 끝났다고 확인 없이 넘어갔다가, 실제로는 오래된 캐시된 페이지를 보고 있거나 다른 브랜치에 올라간 것을 놓치는 경우입니다. 새로고침 후에도 파일이 보이지 않는다면 `git branch`로 현재 브랜치가 정말 `main`인지, `git remote -v`로 원격 URL이 의도한 저장소와 일치하는지부터 다시 점검하는 것이 좋습니다.

## 정리 — 아직 남은 일

이 Step 0 단계에서 아직 체크되지 않은 항목은 모두 **1-3. GitHub·로컬 저장소**에 몰려 있습니다. 정리하면 다음과 같습니다.

- [ ] `git init`과 `git branch -M main`을 이 저장소에서 직접 실행해 결과를 눈으로 확인하기
- [ ] GitHub에서 새 저장소를 만들 때 "Add a README file"을 껐는지 점검하고, 다음 저장소부터는 반드시 꺼 두는 습관 들이기
- [ ] add/add 충돌이 실제로 발생했을 때의 해결 절차(`git add` → `git rebase --continue` → `git push -u origin main`)를 연습해 보기
- [ ] `git rebase --abort`로 되돌리는 경우까지 한 번은 직접 시도해 보기

이 항목들을 실습으로 확인한 뒤에는 [`docs/learning_checklist.md`](../learning_checklist.md)의 해당 체크박스를 실제로 체크하고, Step 1(개별 퀴즈 모델 구현)로 넘어갈 수 있습니다. 더 자세한 실습 코드와 커밋 힌트는 [`docs/learning_guide.md`](../learning_guide.md)의 "Step 0" 절을 함께 참고하세요.
