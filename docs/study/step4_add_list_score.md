## 5-1. add_quiz

체크리스트에는 `add_quiz(self) 구현`이 이번 Step 4의 첫 항목으로 올라와 있지만, 실제로 코드가 작성된 시점은 이번 대화가 아닙니다. `git diff 5ba64a0 1181dea -- main.py`로 Step 3 커밋의 변경 내용을 확인해 보면, `add_quiz`뿐 아니라 `show_quiz_list`·`show_score`·`save_state`·`load_state`까지 `QuizGame` 클래스의 모든 메서드가 "🚧 기능 준비 중입니다" 스텁에서 완전한 구현으로 이미 그 커밋에서 한꺼번에 바뀌어 있었습니다. 즉 체크리스트가 "Step 4"라는 이름을 붙인 5-1(add_quiz)·5-2(show_quiz_list)·5-3(show_score)은, 체크리스트 상 "Step 3" 커밋인 `1181dea` 시점에 이미 전부 구현이 끝나 있었던 것입니다. 이번 대화에서 `main.py`나 `storage.py`에 새로 바뀐 코드가 없다는 사실(`git status`에 두 파일 중 `main.py`가 아예 등장하지 않는다는 점)도 이를 뒷받침합니다. 이는 코드 품질의 문제가 아니라, 체크리스트의 단계 번호와 실제 구현 순서가 항상 정확히 일치하지는 않는다는 것을 보여주는 사례입니다. 학습 문서로서는 이 시점 차이를 짚고 넘어가되, 코드 자체가 무엇을 하는지는 그대로 배워볼 가치가 있습니다.

`add_quiz`의 실제 코드는 다음과 같습니다.

```python
def add_quiz(self) -> None:
    """사용자 입력으로 새 퀴즈를 추가하고 즉시 저장한다."""
    print("\n📌 새로운 자료구조 퀴즈를 추가합니다.\n")
    question = self.ask_text("문제를 입력하세요: ")

    choices: list[str] = []
    for number in range(1, 5):
        choices.append(self.ask_text(f"선택지 {number}: "))

    answer = self.ask_int("정답 번호 (1-4): ", 1, 4)
    self.quizzes.append(Quiz(question, choices, answer))

    if self.save_state():
        print("\n✅ 퀴즈가 성공적으로 추가되었습니다!")
    else:
        print("\n⚠️ 퀴즈는 추가됐지만 파일 저장에 실패했습니다.")
```

먼저 문제 입력에는 `ask_text("문제를 입력하세요: ")`를 씁니다. `ask_text`는 Step 2에서 만든 공통 입력 검증 헬퍼로, 빈 문자열이나 공백만 입력했을 때 다시 물어보도록 되어 있습니다. `add_quiz`는 이 함수를 새로 만들지 않고 그대로 재사용해서 문제 텍스트가 비어 있는 사고를 막습니다.

선택지 4개를 받는 부분이 이번 섹션에서 눈여겨봐야 할 핵심입니다. `choice_1 = self.ask_text(...)`, `choice_2 = self.ask_text(...)` 식으로 네 줄을 나란히 복사해서 쓸 수도 있었겠지만, 실제 코드는 `for number in range(1, 5): choices.append(self.ask_text(f"선택지 {number}: "))` 한 덩어리로 처리합니다. `range(1, 5)`는 1, 2, 3, 4 네 개의 값을 만들어 내므로, 반복문 본문이 정확히 네 번 실행되면서 "선택지 1", "선택지 2", "선택지 3", "선택지 4"라는 프롬프트를 차례로 보여주고 그 결과를 `choices` 리스트에 하나씩 쌓습니다. 이것이 체크리스트가 요구한 "선택지 입력 코드를 4번 복사하지 않고 반복문 또는 동등한 구조로 작성"을 만족하는 방식입니다. 그리고 이 반복문 안에서도 `ask_text()`를 그대로 호출하기 때문에, 네 개의 선택지 각각에 대해 빈 값을 막는 검증이 자동으로 적용됩니다. 별도의 빈 값 검사 코드를 추가로 작성할 필요가 없는 것은, 3-3에서 만들어 둔 `ask_text` 함수를 여기서 그대로 재활용하고 있기 때문입니다.

정답 번호는 `self.ask_int("정답 번호 (1-4): ", 1, 4)`로 받습니다. `ask_int`는 최소값과 최대값을 인자로 받아 그 범위 밖의 숫자나 숫자가 아닌 입력을 걸러내는 헬퍼이므로, 여기서는 1부터 4까지의 범위로 제한해서 호출합니다. 실제 플레이 로그에서 문제 4의 정답 입력 단계에 "5"를 넣었을 때 "⚠️ 1~4 사이의 숫자를 입력하세요."가 뜬 장면이 있는데, 이는 `play_quiz`에서 정답을 확인할 때 쓰인 것과 동일한 범위 검증 로직이며, `add_quiz`의 정답 번호 입력에도 같은 방식으로 쓰이고 있다는 것을 보여줍니다.

문제, 선택지 리스트, 정답 번호를 모두 모으면 `self.quizzes.append(Quiz(question, choices, answer))`로 새 퀴즈를 등록합니다. 여기서 눈여겨볼 점은 `Quiz` 생성자를 그대로 호출한다는 것입니다. 1장에서 배운 것처럼 `Quiz`는 생성 시점에 선택지가 정확히 4개인지, 정답 번호가 1~4 범위인지를 자체적으로 검증합니다. `add_quiz`는 이 검증을 다시 구현하지 않고, `Quiz` 객체를 만드는 순간 그 검증이 자동으로 한 번 더 적용되도록 맡겨 둡니다. `ask_text`·`ask_int`로 입력 단계에서 한 번 걸러지고, `Quiz` 생성자에서 다시 한 번 걸러지는 이중 안전장치인 셈입니다.

마지막으로 `self.save_state()`를 호출해 저장을 시도하고, 그 반환값(성공하면 `True`, 실패하면 `False`)에 따라 서로 다른 메시지를 보여줍니다. 저장에 성공하면 "✅ 퀴즈가 성공적으로 추가되었습니다!"를, 파일 쓰기 등에 실패하면 "⚠️ 퀴즈는 추가됐지만 파일 저장에 실패했습니다."를 출력합니다. 퀴즈 객체 자체는 `self.quizzes`에 이미 추가된 뒤이므로, 저장이 실패하더라도 그 실행 세션 안에서는 방금 추가한 퀴즈를 계속 사용할 수 있고, 다만 프로그램을 재시작하면 사라진다는 차이를 사용자에게 정확히 알려주는 구조입니다. 이 프로젝트에서는 실제로 프로그램을 종료·재시작한 뒤에도 추가한 퀴즈가 남아 있는 것이 확인되어, `save_state()` 호출이 정상적으로 동작하고 있음을 보여줍니다.

흔히 하는 실수는 반복문으로 선택지를 받을 때 `range(1, 5)`를 `range(4)`나 `range(1, 4)`로 잘못 써서 선택지가 3개만 만들어지거나 번호 표시가 0부터 시작하는 경우입니다. 또한 `Quiz` 생성자의 검증만 믿고 `ask_text`·`ask_int`의 사전 검증을 생략하면, 빈 문자열이나 범위 밖 숫자가 일단 함수 안으로 들어갔다가 예외로 튕겨 나오면서 사용자 경험이 나빠질 수 있습니다. 입력 단계에서 미리 걸러내고, 객체 생성 단계에서 한 번 더 확인하는 이중 구조를 유지하는 것이 이 코드의 핵심 설계입니다.

## 5-2. show_quiz_list

### 이 메서드도 이미 구현되어 있었습니다

체크리스트는 이 항목을 "Step 4"의 작업으로 분류하고 있지만, 실제로 `show_quiz_list(self)`가 코드로 작성된 시점은 한 커밋 앞선 Step 3(`1181dea`)입니다. `git diff 5ba64a0 1181dea -- main.py`를 실행해 보면 그 커밋에서 `play_quiz`뿐 아니라 `add_quiz`·`show_quiz_list`·`show_score`·`save_state`·`load_state`까지 `QuizGame` 클래스의 메서드 전체가 "🚧 기능 준비 중입니다" 스텁에서 완전한 구현으로 한꺼번에 바뀌었기 때문입니다. 이번 대화(Step 4)에서 `main.py`에 새로 바뀐 줄은 한 줄도 없습니다(`git status`에 `main.py`가 아예 등장하지 않습니다). 그래서 이 절의 목적은 "코드를 새로 짜는 것"이 아니라, 이미 완성되어 있는 `show_quiz_list`가 체크리스트의 요구사항을 정확히 어떻게 충족하고 있는지 코드 수준에서 확인하는 것입니다.

### 실제 코드

```python
def show_quiz_list(self) -> None:
    """등록된 퀴즈의 번호와 문제만 출력한다."""
    if not self.quizzes:
        print("\n⚠️ 등록된 퀴즈가 없습니다.")
        return

    print(f"\n📋 등록된 퀴즈 목록 (총 {len(self.quizzes)}개)")
    print("-" * 40)
    for number, quiz in enumerate(self.quizzes, start=1):
        print(f"[{number}] {quiz.question}")
    print("-" * 40)
```

### "정답을 노출하지 않는다"는 요구가 지켜지는 방식

체크리스트는 "목록 화면에서 정답 번호나 정답 선택지를 노출하지 않음"을 요구합니다. 이 요구를 지키는 방법에는 두 가지가 있습니다. 하나는 "정답 정보를 읽어온 뒤 화면에는 출력하지 않도록 걸러내는" 방식이고, 다른 하나는 "애초에 정답 정보에 접근하는 코드 자체를 쓰지 않는" 방식입니다. 이 코드는 후자입니다.

`for number, quiz in enumerate(self.quizzes, start=1):` 반복문 안에서 실제로 실행되는 출력 코드는 `print(f"[{number}] {quiz.question}")` 한 줄뿐입니다. 이 줄은 `quiz.question`만 참조하며, `quiz.choices`나 `quiz.answer`는 이 메서드 어디에서도 등장하지 않습니다. 즉 "정답을 숨긴다"는 요구가 지켜지는 이유는 화면에 표시하지 않으려고 별도의 조건문이나 필터링 로직이 들어가 있어서가 아니라, 애초에 그 정보를 꺼내 오는 코드 자체가 존재하지 않기 때문입니다. 이런 방식은 실수로 정답이 노출될 여지 자체를 코드 구조로 차단한다는 점에서, 나중에 유지보수하는 사람이 "혹시 정답이 새어나가는 경로가 있나?"를 걱정할 필요를 없애줍니다.

### play_quiz의 quiz.display(number)와 나란히 비교하기

같은 `main.py` 안에는 `play_quiz`에서 `Quiz` 객체를 화면에 보여주는 또 다른 코드가 있습니다. 바로 `quiz.display(number)`인데, 이 메서드는 문제 텍스트뿐 아니라 선택지 4개까지 전부 출력합니다. 두 코드를 나란히 놓으면 차이가 분명해집니다.

| 화면 | 반복 패턴 | 출력 내용 | 접근하는 속성 |
|---|---|---|---|
| `play_quiz` (문제 풀이) | `for number, quiz in enumerate(self.quizzes, start=1):` | 문제 + 선택지 4개 | `quiz.display(number)` 내부에서 `question`, `choices` |
| `show_quiz_list` (목록 조회) | `for number, quiz in enumerate(self.quizzes, start=1):` | 문제만 | `quiz.question` |

두 메서드는 똑같이 `enumerate(self.quizzes, start=1)` 패턴으로 퀴즈 목록을 순회합니다. 그런데도 한쪽은 선택지까지 다 보여주고 다른 쪽은 문제만 보여주는 이유는, 두 화면의 "의도"가 다르기 때문입니다. `play_quiz`는 사용자가 지금 이 문제를 풀어야 하므로 선택지 정보가 반드시 필요하지만, `show_quiz_list`는 "어떤 퀴즈들이 등록되어 있는지 목록만 훑어보는" 화면이므로 선택지나 정답까지 보여줄 이유가 없습니다. 같은 반복 구조를 재사용하면서도 화면의 목적에 맞게 출력 범위를 다르게 가져간 것입니다.

### 빈 목록 가드도 play_quiz와 같은 패턴입니다

`show_quiz_list`의 첫 줄인 `if not self.quizzes: print("...등록된 퀴즈가 없습니다."); return`은 `play_quiz`에서 퀴즈가 하나도 없을 때 즉시 안내하고 빠져나오는 가드와 사실상 동일한 패턴입니다. `self.quizzes`가 빈 리스트일 때 파이썬에서 `not []`은 `True`이므로, 이 조건문 하나로 "퀴즈가 0개인 경우"를 정확히 걸러낼 수 있습니다. 두 메서드 모두 반복문을 실행하기 전에 먼저 이 가드를 통과시켜, 빈 리스트를 대상으로 `enumerate`를 도는 불필요한 상황(사실 빈 리스트를 순회해도 에러는 나지 않지만, 그 경우 아무 출력도 없이 헤더와 구분선만 찍히는 어색한 화면이 됩니다)을 방지합니다.

### 흔한 실수와 확인 방법

목록 화면을 직접 구현한다면 가장 흔한 실수는 디버깅 편의를 위해 `print(f"[{number}] {quiz.question} (정답: {quiz.answer}번)")`처럼 정답 번호를 슬쩍 끼워 넣어두고 나중에 지우는 것을 잊는 경우입니다. 이 프로젝트의 코드는 애초에 그런 코드를 작성하지 않았기 때문에 이 위험이 없습니다. 새 퀴즈를 추가한 뒤에는 `self.quizzes`가 리스트이고 `add_quiz`가 `self.quizzes.append(...)`로 항목을 늘리므로, 그다음 `show_quiz_list`를 호출하면 `len(self.quizzes)`로 계산되는 총개수와 `enumerate`가 매기는 번호 모두 자동으로 새 항목을 반영합니다. 별도의 카운터 변수를 손으로 관리하지 않고 리스트의 길이와 `enumerate`에만 의존한다는 점이, 항목을 추가하거나 나중에 삭제 기능이 생기더라도 번호와 총개수가 항상 실제 상태와 어긋나지 않도록 보장하는 핵심입니다.

## 5-3. show_score

### 이 메서드도 이미 만들어져 있었습니다

`add_quiz`, `show_quiz_list`와 마찬가지로 `show_score` 역시 이번 대화(Step 4)에서 새로 작성한 코드가 아닙니다. `git diff 5ba64a0 1181dea -- main.py`를 실행해 보면, Step 3 커밋(`1181dea`)에서 `play_quiz`뿐 아니라 `add_quiz`·`show_quiz_list`·`show_score`·`save_state`·`load_state`까지 `QuizGame`의 모든 메서드가 `"🚧 기능 준비 중입니다"` 스텁에서 완전한 구현으로 한꺼번에 바뀌었기 때문입니다. 즉 체크리스트가 "Step 4"로 분류해 둔 5-3 항목은, 체크리스트상 "Step 3" 커밋 시점에 이미 구현이 끝나 있었습니다. 이번 대화에서 `main.py`에 손댄 부분은 없습니다(`git status`에 `main.py`가 전혀 등장하지 않습니다). 그래서 이 섹션은 "새 코드를 짜는 방법"이 아니라 "이미 짜여진 코드가 왜 그렇게 짜여졌는지"를 이해하는 데 초점을 맞춥니다.

### 실제 코드: 3단계 분기

```python
def show_score(self) -> None:
    """최고 점수와 해당 기록의 정답 수를 출력한다."""
    if self.best_total == 0 and self.best_score == 0:
        print("\n⚠️ 아직 퀴즈를 풀지 않았습니다. 먼저 퀴즈를 풀어보세요!")
        return

    if self.best_total == 0:
        print(f"\n🏆 최고 점수: {self.best_score}점")
        print("   (이전 저장 데이터에는 정답 수 정보가 없습니다.)")
        return

    print(
        f"\n🏆 최고 점수: {self.best_score}점 "
        f"({self.best_total}문제 중 {self.best_correct}문제 정답)"
    )
```

이 메서드는 `best_score` 하나만 보지 않고 `best_total`을 기준으로 세 가지 상태를 구분합니다.

1. **`best_total == 0` 그리고 `best_score == 0`** → 아직 퀴즈를 한 번도 풀지 않은 상태입니다. `"⚠️ 아직 퀴즈를 풀지 않았습니다. 먼저 퀴즈를 풀어보세요!"`를 출력하고 바로 함수를 끝냅니다.
2. **`best_total == 0`인데 `best_score > 0`인 경우** → Step 3 문서에서 다룬 구버전 `state.json` 마이그레이션 상황입니다. 정답 수(`best_correct`)와 전체 문제 수(`best_total`) 필드가 없던 이전 형식의 저장 파일을 불러온 경우로, 점수만 있고 몇 문제 중 몇 문제를 맞혔는지는 알 수 없습니다. 그래서 점수만 출력하고 `"(이전 저장 데이터에는 정답 수 정보가 없습니다.)"`라는 안내를 덧붙입니다.
3. **둘 다 있는 정상 상태** → 점수, 정답 수, 전체 문제 수를 모두 담아 `"🏆 최고 점수: 100점 (5문제 중 5문제 정답)"` 형태로 출력합니다.

### 왜 `best_score`가 아니라 `best_total`로 "미풀이"를 판단할까요

여기서 중요한 것은 첫 번째 분기가 `best_score == 0`이 아니라 `best_total == 0`을 기준으로 삼는다는 점입니다. 만약 사용자가 실제로 퀴즈를 풀었는데 한 문제도 못 맞혀서 진짜 0점을 받았다면 어떻게 될까요? 이 경우 `best_correct`는 0이 되지만, `best_total`은 풀었던 문제 수(예: 5문제 중 풀었다면 5)로 여전히 0보다 큽니다. 즉:

| 상태 | best_total | best_score | best_correct |
|---|---|---|---|
| 한 번도 안 풀어봄 | 0 | 0 | 0 |
| 5문제 풀어서 전부 틀림(실제 0점) | 5 | 0 | 0 |
| 5문제 풀어서 5문제 정답 | 5 | 100 | 5 |

만약 판단 기준을 `best_score == 0`으로만 잡았다면, "5문제를 풀었지만 전부 틀려서 0점을 받은" 정당한 기록까지 "아직 퀴즈를 풀지 않았습니다"로 잘못 안내하게 됩니다. `best_total == 0`은 "아직 한 번도 채점이 이루어지지 않았다"는 사실만을 정확히 걸러내므로, 실제 0점 기록과 미풀이 상태를 혼동하지 않을 수 있습니다.

### 실제 플레이 로그로 확인하기

이 로직이 실전에서 방어적으로 잘 동작한다는 것은 사용자가 직접 실행한 로그로도 확인됩니다. Step 3에서 5문제를 모두 맞혀 `best_score = 100`, `best_total = 5`, `best_correct = 5`인 기록이 이미 저장되어 있는 상태에서, 새로 퀴즈를 풀어 이번에는 2문제만 맞혔습니다.

```
========================================
🏆 결과: 5문제 중 2문제 정답! (40점)
========================================

선택: 4

🏆 최고 점수: 100점 (5문제 중 5문제 정답)
```

40점을 받았는데도 `"🎉 새로운 최고 점수"` 같은 갱신 메시지 없이 결과만 출력되었고, 이어서 메뉴 4번(점수 확인)을 선택하자 여전히 이전 최고 기록인 `"100점 (5문제 중 5문제 정답)"`이 그대로 표시되었습니다. 이것은 Step 3에서 만든 "새 점수가 기존 `best_score`보다 높을 때만 갱신"하는 로직이 실제 플레이에서 낮은 점수를 무시하고 기존 기록을 지켜냈다는 증거입니다. 동시에 체크리스트의 마지막 항목인 "퀴즈 풀이 뒤 최고 점수 확인 메뉴에서 갱신된 기록이 표시되는지 확인"도 이 로그를 통해 실제로 검증되었습니다 — 다만 여기서 "갱신"이란 "높은 점수로 실제로 바뀌었는지"뿐 아니라 "낮은 점수 앞에서 잘못 바뀌지 않았는지"까지 포함하는 확인이었습니다.

### 흔한 실수

- 미풀이 판단을 `best_score == 0`으로 하면 앞서 표에서 본 것처럼 "실제 0점" 기록을 미풀이로 오인합니다. 반드시 `best_total`처럼 "채점이 이루어졌는가"를 나타내는 값을 기준으로 삼아야 합니다.
- 구버전 `state.json`처럼 `best_total`, `best_correct` 필드가 아예 없을 수 있는 저장 파일을 다룰 때는, 이 필드들이 없다고 가정하고 바로 `f"{self.best_total}문제 중 ..."`을 출력하면 `0문제 중 0문제 정답`처럼 의미 없는 문구가 나올 수 있습니다. 이 코드처럼 `best_total == 0`인 경우를 별도로 걸러 점수만 보여주는 분기가 필요합니다.
- 점수 확인 로직을 검증할 때 "높은 점수로 갱신되는 경우"만 테스트하고 끝내기 쉽습니다. 이번 로그처럼 일부러 낮은 점수를 받아 "기존 기록이 그대로 유지되는지"도 함께 확인해야 갱신 조건(`>` 비교)이 제대로 동작하는지 검증할 수 있습니다.

## 5-4. Step 4 Git·스크린샷

### 커밋과 push는 이미 끝나 있습니다

먼저 확인할 것은 "커밋해야 한다"가 아니라 "커밋이 이미 됐다"는 사실입니다. `git log`로 이력을 보면 다음과 같습니다.

```bash
$ git log --oneline --graph --all --decorate
* 677163a (HEAD -> main, origin/main) Feat: 퀴즈 추가 기능 및 입력 유효성 검사 구현 퀴즈목록 조회 기능 구현 최고점수 확인 긴으 구현
*   0e84cc0 Merge: 퀴즈 풀기 기능 병합
```

`HEAD`와 `origin/main`이 동시에 `677163a`를 가리키고 있습니다. 즉 로컬에서 커밋을 만든 뒤 원격 저장소로 push까지 이미 끝난 상태입니다. 체크리스트의 "커밋 #11까지 git push 실행" 항목은 결과만 보면 충족된 것처럼 보입니다. 하지만 그 커밋 하나(`677163a`)의 내용을 들여다보면 이야기가 달라집니다.

### 커밋 메시지와 실제 diff가 다른 이야기를 합니다

`git show --stat 677163a`로 이 커밋이 실제로 무엇을 바꿨는지 확인하면 다음과 같이 나옵니다.

```
commit 677163a Feat: 퀴즈 추가 기능 및 입력 유효성 검사 구현 퀴즈목록 조회 기능 구현 최고점수 확인 긴으 구현

 docs/screenshots/step3.png           | Bin 0 -> 141812 bytes
 docs/study/step3_play_quiz_branch.md | 308 +++++++++++++++++++++++++++++++++++
 2 files changed, 308 insertions(+)
```

메시지와 diff를 나란히 놓아 보면 둘이 완전히 다른 대상을 가리키고 있다는 것이 분명해집니다.

| 커밋 메시지가 말하는 것 | 실제 diff에 있는 것 |
|---|---|
| 퀴즈 추가 기능 및 입력 유효성 검사 구현 | `docs/screenshots/step3.png` (Step 3 스크린샷, 신규) |
| 퀴즈목록 조회 기능 구현 | `docs/study/step3_play_quiz_branch.md` (Step 3 학습 노트, 308줄 신규) |
| 최고점수 확인 기능 구현 | *(main.py·storage.py 변경 없음)* |

`main.py`도 `storage.py`도 이 diff에 단 한 줄도 등장하지 않습니다. 커밋 메시지는 코드 작업 세 가지를 설명하고 있지만, 실제로 커밋에 담긴 것은 이전 Step에서 만들어졌던 문서 파일 두 개뿐입니다.

### 왜 이런 일이 벌어졌을까요

이 미스터리를 풀어 주는 단서가 `git diff 5ba64a0 1181dea -- main.py`에 있습니다. Step 3 커밋(`1181dea`)에서 이미 `add_quiz`, `show_quiz_list`, `show_score`를 포함한 `QuizGame`의 모든 메서드가 "🚧 기능 준비 중입니다" 스텁에서 완전한 구현으로 한꺼번에 바뀌어 있었습니다. 즉 체크리스트가 "Step 4"로 이름 붙인 코드 작업은, 실제로는 한 커밋 앞선 Step 3 시점에 전부 끝나 있었던 것입니다.

그렇다면 `677163a` 시점에 `git add .`를 실행했을 때 스테이징 영역에 올라온 것은 무엇이었을까요? `main.py`·`storage.py`는 이미 `1181dea`에서 커밋되어 더 이상 변경 사항이 없었으므로, 실제로 새로 스테이징된 것은 이전 대화(Step 3)에서 만들어졌지만 그때 커밋하지 않고 남겨 둔 두 파일—`step3.png`와 `step3_play_quiz_branch.md`—뿐이었습니다. 그런데 커밋 메시지는 아마 Step 4 작업을 위해 미리 준비해 둔 문구를 그대로 붙여 넣으면서, 실제로 스테이징된 내용과 무관하게 "퀴즈 추가·목록 조회·최고 점수 확인 구현"이라는 문구가 커밋에 실렸습니다.

### Step 1~3의 문제와는 다른 종류입니다

Step 1~3에서 반복됐던 문제는 "계획한 커밋 2개가 1개로 합쳐진다"는 것이었습니다. 이번 `677163a`는 겉보기에 비슷해 보이지만 본질이 다릅니다.

| 구분 | Step 1~3의 문제 | Step 4(`677163a`)의 문제 |
|---|---|---|
| 증상 | 커밋이 계획보다 적게 만들어짐 | 커밋 개수는 문제가 아님 |
| diff 안에 관련 코드가 있었나 | 있었음 (여러 작업이 한 커밋에 뭉쳐짐) | 없었음 (메시지가 설명하는 코드가 diff에 아예 없음) |
| 원인 | 커밋 시점을 나누지 않고 한 번에 add·commit | 그 코드가 이미 이전 커밋에 들어가 있는 상태에서, 남은 무관한 파일에 옛 메시지가 붙음 |

앞의 문제는 "너무 많이 묶었다"이고, 이번 문제는 "메시지가 가리키는 내용이 그 커밋 안에 없다"입니다. 커밋 이력만 보고 "add_quiz는 여기서 구현됐구나"라고 믿으면 실제 코드 위치를 완전히 잘못 짚게 됩니다.

### 커밋 직전 습관이 있었다면 바로 알아챌 수 있었습니다

`docs/learning_checklist.md` 최상단의 "모든 기능 커밋에 적용할 공통 규율"에는 이미 다음 두 가지가 적혀 있습니다.

```bash
git status                # 변경된 파일 확인
git diff --cached         # 다음 커밋에 들어갈 변경 내용 검토
```

만약 `677163a`를 커밋하기 직전에 이 두 명령을 실제로 실행해 봤다면, `git status`에서 `main.py`가 전혀 언급되지 않는다는 것과 `git diff --cached`에 이미지 바이너리 한 개와 마크다운 문서 한 개만 걸려 있다는 것을 바로 눈으로 확인할 수 있었을 것입니다. 그랬다면 "퀴즈 추가·목록 조회·점수 확인을 구현했다"는 메시지를 이 커밋에 붙이는 것이 부적절하다는 것을 커밋 전에 알아챘을 것입니다. 이 두 명령은 문서 맨 위에 이미 규율로 적혀 있었지만, 이번 커밋에서는 실천으로 이어지지 않았습니다.

### 체크리스트가 요구한 것과 실제로 있었던 일
